Ops 工具集

dsh-ops 开发工具 ·team ·更新于 2026-11-18 ·⧉ 复制提示词 128 次

Ops 工具集

给 DSH 补一组底层操作工具：批量读文件、按行号切片、结构化 diff。目标是减少往返轮次，从而降低 Token 消耗与任务耗时。

包含能力

  • ops.read_range 按行号范围读取大文件片段
  • ops.diff 输出结构化 diff，而不是整文件重写
  • ops.batch 一次调用完成多文件读取

dsh plugin --profile work list

发布设置

提交权限与是否需要审核由该空间的发布策略决定；更新版本时此项禁用、不可更改（PRD §6.3）。
空间公开时进入索引源，DSH「发现」页可搜到。

提交前校验

  • ✓npm 包存在，latest 版本可读取
  • ✓Git 仓库可达，默认分支可读取
  • ✓package.json 可解析
  • ✓name 合法，version 是精确 SemVer
  • ✓未标记 private
  • ✕ 拒绝这不是 DSH 插件：缺少 dsh.bundle 声明，装进 DSH 也不会生效（提交前校验不通过，当场拒绝）
  • ·该版本是否已存在（提交时校验）
  • ·图标 ≤ 32 KiB
简介与图标取自包内声明；显示名称默认取包内名称，可另行修改。要改包内声明的内容，请更新包后重新提交——索引必须与实际可安装的那一份包一致。

提交前将再次核对版本与展示信息。

确认提交信息

Ops 工具集 @team/dsh-ops@1.4.0 可见性：公开 降低 Token 消耗 提交后的处理取决于可见性和安全扫描策略。请以本次提交回执及版本状态为准。

  1. 01 四种提交来源最终只收敛为 npm / git 两种分发来源（用户侧只写"发布 / 上架"，不展开内部处理）
  2. 02 zip 与文件夹必须含合法 package.json 且声明 dsh.bundle，提交前校验不通过当场拒绝；通过则 202 异步受理进入排队中（不产生同步 422，也不留版本记录）
  3. 03 版本冲突返回 409：Git 提示"请先在仓库中升级版本号再提交"，npm 提示"该版本已存在，请先在上游 npm 发布新版本后重新提交"
  4. 04 发布失败（仅 zip / 文件夹来源）保留审核结论：个人空间停「待发布」、团队空间停「已通过审核，等待发布」；两态都没有可安装制品、不进索引，作者可见脱敏原因并可重试，重试成功才上架；npm 与 git 来源不经这一步，审核通过即上架（PRD §6.5 / §6.6 / 验收 17）
  5. 05 审核与否由空间策略决定，提示文案随空间变化
  6. 06 插件包文件支持 zip 与文件夹两种选择方式；浏览器不支持目录选择时，用 zip 上传
  7. 07 npm 来源无版本输入框、任何途径传入版本都不受理；版本取 latest 跳过 prerelease 并在提交时冻结，审核 / 发布不重新解析（PRD §6.3 / §6.6）
  8. 08 Git 来源无子目录输入框、也无分支 / tag / commit / 凭据输入框；API 夹带 path（子目录）同样不受理——一个插件一个仓库，包在仓库根目录（PRD §6.2 / §6.3）
  9. 09 可见范围决定是否进公共索引：公开 + 空间公开才进索引；「仅命名空间」不进索引、仅该空间成员站内可见；「私有」仅作者本人可见（PRD §6.3 / §8.2 / §8.4）。右栏「发布设置」与技能发布页同构：命名空间、可见范围常驻可见、可下拉选择，更新版本时命名空间禁用；选到「公开」以外时，可见范围下方立刻出现醒目提示「不会进入索引源」，不需要等到提交才知道
  10. 10 提交是两步、不是一步：页脚只有一颗「下一步：确认」，点开「确认提交信息」弹窗（显示名称 / `@namespace/name@version` / 可见性 / 简介 / 末行审核说明文案，与技能发布页确认弹窗同款），弹窗里「返回编辑」回到表单、「确认发布」才真正提交（PRD §6.3）
  11. 11 提交插件在控制台布局内：左侧导航常驻、内容区右侧展开；页头左上角「返回我的插件」固定回到「我的插件」列表（不靠浏览器后退、不按来源改目标；对齐套件新建 / 编辑页的 SuiteWorkspaceHeader）
