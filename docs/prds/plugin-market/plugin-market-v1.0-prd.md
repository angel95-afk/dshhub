# PRD: DSH 插件市场 v1.0

**版本**: v2.18（冻结版） ｜ **日期**: 2026-11-26 ｜ **状态**: Frozen（待开发对齐）
**本版保留的语义基线**: 提交异步受理；不统计下载、无「仅收录」；包名全站唯一且提交即校验；图标只取包内声明；不设灰度发布。

## 1. 背景与目标

本站目前只托管一类资产：SkillHub 技能（`SKILL.md` 包，经 CLI 装入 Agent 技能根）。DSH 自身还有另一套扩展机制——**DSH 插件**（npm 包 + `dsh.bundle` 声明，经 `dsh plugin add` 安装），形态、安装入口与能获得的能力完全不同。DSH 官方已定义**插件市场索引协议**（`format: 1` 的 JSON 索引）：用户在 DSH「插件 → 实验性插件 → 自定义插件索引」打开开关，在「发现」页添加索引源 URL，即可浏览并安装索引中的插件。本站要做的是**成为这样一个索引源**，并承接组织内部的插件提交与治理。参考站 `dsh-hub.cc` 与 `dsh.market`；本站差异点是**组织内部分发 + 命名空间治理 + 审核审计**，不做公网爬取。

### 1.1 产品目标

1. **一键闭环"发现 → 安装"**：用户一次拿到两样东西——可添加的索引源地址（市场页）与可复制给 Agent 的安装提示词（详情页）。
2. **内部插件有正规入口**：四种来源提交，全过程状态可解释、失败可重试，进目录后始终符合官方索引协议，且"可安装"与"已上架"严格等价。
3. **发布收进内容上下文**：把「发布」从全局导航收进市场页，浏览与发布在同一上下文完成；插件侧入口与技能侧对称。
4. **装之前看得见**：用 `dsh-trust-check` 做静态能力披露 + 红线闸门，用户能看到插件会碰什么，红线默认挡住。

### 1.2 非目标（本期不做）

- DSH 内的商店插件（在 DSH 界面直接浏览本站目录）——需另发一个 dsh 插件，独立立项；CLI 插件子命令（`skillhub plugin install/list`）。
- 外部热度指标（`github_stars`、`npm_weekly_downloads`）与分发量接入；插件评分、评论、场景包、插件与技能互推。
- **运行时行为观测**（沙箱动态执行、真实流量、调用链）——本期只有静态披露，局限已在 §7.1 对用户明示。
- 安全背书：不出具"安全 / 已认证 / 无风险"结论，不做漏洞定级（§7.1）。
- 站内 tarball 下载、「仅收录」类目、登记已在镜像中的 `name@version`（§6.4）；灰度发布与按空间放量。
- **举报只做入口**：详情页给举报入口，处置流程与责任方不在本期（§5.1）。
- 空间级批量操作（只提供漂移重扫的差异清单与筛选，§7.4）。

## 2. 名词与边界

| 术语 | 定义 | 易混点 |
|---|---|---|
| **DSH 插件** | npm 包形态分发、声明 `dsh.bundle`、由 `dsh plugin add` 安装的扩展；**归属一个命名空间（个人或团队）**，是独立于技能的第二类资产 | 不是技能，不含 `SKILL.md` 入口约定 |
| **SkillHub 技能** | `SKILL.md` 技能包，装入 `.dsh/skills` 等技能根 | 两套资产，不共用表与状态机 |
| **插件市场** | 本站 `/plugins` 门户页 | 与 `/search`（技能市场）并列 |
| **索引源** | 索引文件的 URL，由用户加入 DSH「发现 → 添加索引源」，属于当前 profile | 不是 npm registry 地址 |
| **索引文件** | 符合官方 `format: 1` 的 JSON，固定入口 `/dsh/index.json` | 全站一份，不按分类拆分 |
| **安装提示词 / 安装文档** | 提示词是详情页复制给 Agent 的一段自然语言，指向该插件某个**确定版本**的安装文档；文档为 `/dsh/install/{ns}/{slug}/{version}.md` | 提示词只在详情页；文档不是给人看的详情页 |
| **提交来源 / 分发来源** | 提交来源四种：npm 包名 / 内网 Git / zip / 文件夹；分发来源只有 `npm` 或 `git`（协议规定） | 两回事，提交来源需收敛为分发来源（§6.2） |
| **能力披露** | 对源码的静态判定：会碰什么能力 + 红线 + `文件:行号` 证据 | 不是安全评级，不是漏洞列表 |
| **裁决** | 扫描四态：未检出风险信号 / 需确认 / 有红线 / 扫描失败 | 不看排序分，分数低也可能是"需确认" |
| **红线** | 五类硬信号：安装脚本、核心 bundle 篡改、读凭据且有网络、明文 `http://`、字面量 IP 外连 | 文案由工具冻结，本站不自造 |
| **索引状态** | 该插件当前是否进公共索引，以及不进的唯一原因（§3.4） | 与"上架状态"是两件事：私有空间可上架但不进索引 |
| **可见范围** | 插件三档可见性：`PUBLIC` 公开 / `NAMESPACE_ONLY` 仅命名空间 / `PRIVATE` 私有，取值与标签沿用技能侧（§6.3） | 不是"上架状态"：已上架但可见范围非 `PUBLIC` 仍不进公共索引（§8.2、§8.4） |

> 术语沿用 `../../../CONTEXT.md`：不得把"SkillHub 技能"统称为"DSH 插件"，不得用"接入 DSH"同时指代插件托管与技能消费。

## 3. 信息架构与入口

### 3.1 顶部导航

现状 `首页 / 发布 / 技能市场 / 技能套件 / 控制台` → 改造后 `首页 / 技能市场 / 插件市场 / 技能套件 / 控制台`：

- 原「发布」（`/dashboard/publish`）从导航移除，位置由「**插件市场**」（`/plugins`）接替，但**排在技能市场之后**——插件侧依赖 DSH 的实验性开关、v1 无存量内容，不宜占第二导航位。
- 「发布」改由技能市场页头「发布技能」主按钮承接（登录后可见，跳 `/dashboard/publish`）；页脚「产品」栏发布链接保留作次级入口；移动端菜单跟随同一数据源。
- 「我的技能」的更新 / 重新提交流程仍深链 `/dashboard/publish` 及其**原有查询参数**，导航改动不得破坏该链路。

### 3.2 页面与路径

| 页面 | 路径 | 谁可访问 | 说明 |
|---|---|---|---|
| 插件市场 | `/plugins` | 匿名 | 两模块页面（§4） |
| 插件详情 | `/plugins/{namespace}/{slug}` | 匿名（私有空间仅成员） | 版本、安装、README、披露（§5） |
| 提交插件 | `/dashboard/plugins/submit` | 登录 + 空间成员 | 四来源表单（§6） |
| 我的插件 | `/dashboard/plugins` | 登录 | 我提交的插件、在途提交与索引状态 |
| 命名空间插件管理 | `/dashboard/namespaces/{slug}/plugins` | 登录 + 空间成员 | 空间维度列表与管理（§3.4） |

导航高亮沿用现有严格匹配规则；`/plugins` 与 `/dashboard/plugins` 不互相点亮。

### 3.3 「我的插件」三个入口（必须同构，不能只藏在侧栏）

| 位置 | 技能侧 | 插件侧（本期） |
|---|---|---|
| 市场页头 | 我的技能（次级）+ 发布技能（主按钮） | **我的插件**（次级）+ 提交插件（主按钮） |
| 控制台侧栏「技能与数据」组 | 我的技能、我的套件、命名空间… | 在「我的技能」之后插入 **我的插件** |
| 控制台概览卡片区 | 我的技能卡 | 新增 **我的插件** 卡（同级） |
| 命名空间详情 | 技能 tab | 新增 **插件 tab**（§3.4） |

- 市场页头两个按钮**登录后渲染，未登录都不渲染**；「提交插件」主按钮，「我的插件」次级按钮。技能市场页头若当前只剩「发布技能」，一并补「我的技能」次级按钮，保证两个市场按钮组完全对称。
- **「我的插件」以提交为单位**：除插件 / 版本列表外，必须单列在途提交（阶段、已等待时长、失败原因与下一步），作者离开提交页后仍能看到自己在排队 / 扫描 / 待审 / 待发布的提交。

### 3.4 命名空间详情「插件」tab

现有 tab 为 `技能 / 成员 / 审核 / 设置`，本期在「技能」后插入**插件** tab → `技能 / 插件 / 成员 / 审核 / 设置`。

- **内容**：该空间下全部插件，**含待审核、待发布、已下架**。列：插件（图标 + 标题 + npm 包名）、最新版本、状态、分类、裁决、**索引状态**、提交人、更新时间、操作；筛选支持状态、关键词（标题或包名）、分类、**漂移重扫命中**。
- **索引状态**（与市场同源判定，用于回答"为什么搜不到"）：`已收录` ／ `待重建` ／ `未收录：空间为私有` ／ `未收录：可见范围非公开` ／ `未收录：最新版本裁决为有红线` ／ `未收录：无已上架版本`。「我的插件」同样有这一列。
- **操作（按权限显示）**：空间管理员可下架 / 恢复上架 / 撤下单版本 / 改分类 / 改可见范围 / 看完整扫描报告 / 重新扫描 / 进入该空间审核队列；作者本人可看详情、看拒绝原因、重试待发布、改可见范围、重新提交；普通成员只读。页头右侧「提交插件」主按钮，携带命名空间参数预填。
- **可见性与空态**：tab 对所有空间成员可见（含个人空间所有者），「成员」tab 仍只对团队空间可见；空态区分"空间还没有插件"（给提交入口）与"筛选无结果"（给清空筛选）。
- **不做**：空间级批量操作、跨空间迁移（迁移走删除 + 释放包名，见 §8.5）。

## 4. 插件市场页（`/plugins`）

自上而下**两个模块**，顺序固定：① 索引源 → ② 插件列表。

### 4.1 模块一：索引源

**目的**：让用户把本站加进 DSH 的索引源列表。

- 主展示：索引文件地址，等宽字体 + 复制按钮（复制成功态 2 秒）；地址按站点部署配置生成（含子路径前缀），前端不硬编码。状态：加载中骨架 / 加载失败显示"索引暂不可用"**但保留地址可复制** / 索引为空显示"暂无已上架插件"。
- 三步说明（与 DSH 实际入口一致）：① 打开 DSH「插件」，在「实验性插件」下启用「自定义插件索引」；② 切到「发现」，点「添加索引源」，粘贴地址；③ 保存后即可在「发现」页浏览、搜索、安装。提示：索引源属于当前 profile；`http:` 索引可被网络路径上的他人篡改，生产必须用 `https:`。

### 4.2 模块二：插件列表

- **页头按钮**：我的插件（次级）+ 提交插件（主按钮），登录后渲染（§3.3）。
- **工具栏**：关键词搜索（输入停顿后才查询）、9 个分类按钮组（单选，可"全部"）、结果数、排序（最新 / 名称）；网格卡片 2/3/4 列响应式。
- **卡片**：图标（无图标用首字母占位）、标题（缺省显示 npm 包名）、一句话简介、分类徽标、作者、最新版本号；"需确认"/"有红线"带裁决徽标。**卡片上不展示任何计数**（浏览数、复制次数都不展示），也**不放**"复制提示词"按钮（提示词需带确定版本，只在详情页生成，§5.2）。整卡可点进详情。
- **空 / 异常态与分页**：无结果给"清空筛选"；请求失败可重试；**空索引时的空态要带"成为第一个收录的插件"入口**；每页 24，底部"加载更多"（不做页码，与搜索页一致）。**默认排序 = 发布时间倒序**，不声明"外部指标排序"。

### 4.3 明确不做：市场页提示词模块

市场页**不提供**任何 DSH 安装提示词。提示词按"插件 + 确定版本"生成，全站只在详情页出现：市场页只能写通用句式，Agent 拿到后仍要猜装哪个包；两处并存还会让用户以为要各复制一次。

## 5. 插件详情页

### 5.1 页面结构与内容

| 区域 | 用户看到什么 |
|---|---|
| 头部 | 图标、标题、npm 包名（可复制）、分类、作者、最新版本、`更新时间`、`复制提示词次数` |
| 安装区 | **只读**的「当前最新版本 1.4.0」文本（无下拉 / 无单选 / 无输入框）→ 安装提示词 + 复制；折叠区给等价命令 `dsh plugin --profile <profile> add {name}@{version} --ignore-scripts` |
| 来源 / 兼容性 | npm（含 registry 地址）或 git（**仓库地址 + 提交号**，均为服务端解析出的最终值，不是用户原话）；不展示子目录（Git 来源只有一个仓库地址输入框，插件包按规定位于仓库根目录）；仓库 / 主页外链；`engines.dsh`（未声明时显示"未声明，装前请自行确认"） |
| 披露区块 | 裁决、能力清单、红线列表、证据折叠（`文件:行号` + 片段）、工作区外路径 / 密钥触摸 / 字面量去向、扫描器版本与时间、免责与已知局限；红线经管理员放行时显示"管理员已确认风险"+ 理由摘要（§7） |
| 正文 | README（提交时快照，Markdown 渲染；图片只允许 `https:` 外链） |
| 版本列表 | **只读历史**：版本号、发布时间、来源、`engines.dsh`、该版本裁决徽标，最新版标「最新」；**不提供任何逐版本复制 / 安装入口** |
| 底部 | 举报入口（处置流程不在本期，"查看我的插件"给作者本人） |

- **两个时间的语义固定**：`更新时间` = 最近一次元数据变更（分类 / 简介 / 图标），**不参与索引排序**；索引排序与"版本发布时间"只看版本首次进入已上架的时间（撤版后重新上架不刷新）。
- **复制提示词次数**：唯一对外展示的计数，标注"按来源去重，内网共用出口时会偏低，仅供参考"（口径见 §10）。
- **页面不提供任何选版本的控件**：无下拉、无单选、无输入框、无「安装此版本」按钮、无逐版本复制入口——安装永远按**当前最新已上架版本**进行。**这不等于安装文档不带版本段**（§5.2）：提示词与文档仍落到唯一确定版本，只是那个版本由服务端在**复制那一刻**取最新已上架版本，不由用户选择。理由：让用户选版本会产生"两个人拿到的提示词不一样"的支持成本，历史版本用于回溯而非安装。

### 5.2 安装提示词（全站唯一入口，永远指向确定版本）

```
请按照 {站点地址}/dsh/install/{namespace}/{slug}/{version}.md 安装 DSH 插件 {npm 包名}@{version}。
```

- **必须带版本段**：同一插件有多个已上架版本，文档必须能落到唯一版本，否则 Agent 会装错版本且不报错。**版本段取复制那一刻的最新已上架版本，不由用户选择**（页面没有任何选版本入口，§5.1）。提示词里的包名用 npm 包名而非 `namespace/slug`（官方安装 spec 是 `name@version`），站点地址由后端下发、前端不拼接，子路径部署必须带前缀。
- 详情页安装区**固定只有一个**「复制提示词」，版本列表没有逐版本复制入口。**产品契约：复制到的提示词装的就是提示词里写的那一个版本**——版本由服务端渲染，前端不拼、不替换。
- **旧路径兼容**：`/dsh/install/{ns}/{slug}.md`（无版本段）保留为别名，内容为"当前最新已上架版本"，**直接 200 返回、不做重定向**，供已经记住旧句式的 Agent 使用；插件存在且已上架时永不 404。

### 5.3 安装文档内容（Agent 视角）

`/dsh/install/{namespace}/{slug}/{version}.md` 按模板生成，顺序固定 7 段：① 一行标题 + 一句话说明；② **需要安装的内容**（包名、精确版本、`engines.dsh` 要求、来源）；③ **安装步骤**（确认 Profile 名 → `dsh plugin --profile <profile> add {name}@{version} --ignore-scripts` → 提示"不要省略 `--ignore-scripts`"）；④ **校验**（`dsh plugin --profile <profile> list` 中应出现该包与版本；说明"仅包安装成功，不代表功能可用"）；⑤ **卸载**（`dsh plugin --profile <profile> remove {name}`）；⑥ **提示**（包来源、是否执行安装脚本、请核对来源与版本 + 一行能力披露摘要）；⑦ **取不到包时**：正文固定写"**本站的包分发地址已开放匿名只读，无需配置凭据；若报权限错误请联系管理员**"（不写 token 配置流程）。

文档中不得出现任何 Token 或凭据。`index.md` 同模板，改为"如何添加索引源 + 目录概览"，列出不超过 50 个插件，其余指向站点；**市场页不展示指向它的提示词模块**（避免与详情页形成两套话术）。

## 6. 提交插件（四种来源）

### 6.1 入口与权限

三处入口均落到 `/dashboard/plugins/submit`：`/plugins` 页头、`/dashboard/plugins` 页头、命名空间插件 tab 页头（带命名空间参数预填）。需登录、需为所选命名空间成员（不低于普通成员）。

**发布策略只按空间，不看成员**：个人空间免审——扫描通过即上架（zip / 文件夹来源需先由平台发布成功，§6.2）；团队空间需审核——扫描通过后**先审核**，审核通过才对外提供安装、**上架成功才进索引**；**审核拒绝即不发布**（不产生任何制品、不进索引，§6.5）。**不复用技能侧的"成员级免审授权"**（技能写得好不等于可以发布任意代码），该项只作用于技能。

**入口可用性的通用规则（对任何"某类空间暂不支持"的场景都适用）**：提交入口是否可用，由"该空间当前是否开放提交能力"决定；**不可用时置灰并说明原因，不隐藏入口**——入口消失会让用户以为功能没了，反而产生工单（当前实例见 §12 P0：团队空间待**审核**能力就绪后开放）。

### 6.2 四种提交来源与收敛规则

官方索引只允许两种分发来源（`npm` / `git`），四种提交来源必须收敛：

| 提交来源 | 用户操作 | 收敛为 |
|---|---|---|
| **npm 包名** | **只填包名（可 scoped），禁止输入版本**；分支 / tag / commit / 凭据同样不填 | 查 registry 取**最新非预发布版本**（提交时冻结）→ `npm` |
| **内网 Git** | **只有一个输入框：仓库地址（必填）**（`https://host/group/repo` 或 `git@host:group/repo.git`，内部归一）；**禁止填子目录**——一个插件一个仓库，插件包必须位于**仓库根目录**，位置由规范决定、不是用户选项；**不填分支、不填 tag、不填 commit**——一律取该仓库**默认分支的最新提交**；**凭据由平台配置，用户不填任何凭据** | 提交前先**预检**并按类型分别提示：地址不可达 / 无权限 / 仓库不存在 / 不在允许范围内；预检通过后取默认分支最新提交，再按 §6.4 第 6 条校验仓库根目录的 `package.json` → `git` |
| **zip 压缩包** | 上传 zip | 解压校验后规范化为 npm 包，**由平台发布成 npm 包** → `npm` |
| **文件夹** | 选择本地目录 | zip 的 UI 变体：**前端打包为 zip 后走同一链路**，不是独立链路 → 同 zip |

- 对用户而言"文件夹"就是一种上传方式；浏览器不支持选目录时提示改用 zip（zip 始终是主路径）。zip / 文件夹必须能解析出合法 `package.json` 且能被平台发布成 npm 包，否则直接拒绝——**没有可分发位置就不能上架**（§8.6）。
- **只有 zip / 文件夹来源需要平台代用户发布**：这两种上传内容原本不在任何可分发的源上，平台必须先把它规范化成 npm 包并放进内部源，才能进索引、被 `dsh plugin add` 装到；**npm 来源的包本来就在源上，Git 来源按仓库地址 + 提交号分发，这两者都不需要代发**。**这是内部实现差异，不得出现在任何用户可见文案里**——审核页、进度、失败原因、风险提示只写"发布 / 上架"，不写"代发"、不写"内部源"。

### 6.3 表单：全自动为原则，人工只选四样

**"四样"的计数口径先说清**：命名空间、**可见范围**、提交来源（**含**其来源参数——Git 仓库地址 / npm 包名 / zip / 目录）、分类。来源参数并入"提交来源"一项、不单独计数（历史表述里的"三样"即漏掉了本次新增的可见范围）。字段分两处放：**命名空间与可见范围在右侧常驻「发布设置」区**（与技能发布页同构，滚动时保持可见），提交来源与分类在主列表单。

用户**只填**：命名空间、**可见范围**、提交来源（四选一，含来源参数）、分类（9 类必选 1）。其余全部从包内元数据解析、**只读不可编辑**：包名、版本、`engines.dsh`、标题、简介、图标、README、仓库地址。

**可见范围三档（取值与中文标签沿用技能侧，不新造词；必选、无"留空"）**：

| 取值 | 用户看到的标签 | 是否进公共索引 | 谁能看到 |
|---|---|---|---|
| `PUBLIC` | 公开 | 空间公开时**进**公共索引（§8.2），DSH 用户在「发现」页可搜到 | 站内匿名可见 |
| `NAMESPACE_ONLY` | 仅命名空间 | **不进**公共索引 | 仅该命名空间成员站内可见；非成员按未上架处理（§8.4） |
| `PRIVATE` | 私有 | **不进**公共索引 | 仅作者本人可见；空间 OWNER / ADMIN 与超级管理员仍可按治理规则访问（沿用技能侧口径，不额外扩张） |

- **可见范围的变更分两条路；命名空间与来源提交后不可改**：「命名空间与来源提交后不可改」这条照旧成立，**不可改的只有这两项**。
  - **缩窄**（`PUBLIC` → `NAMESPACE_ONLY` → `PRIVATE`）：由插件作者或该空间管理员在「我的插件」/ 命名空间插件 tab **直接改、立即生效**。
  - **放宽**：**v1 不提供"单改可见范围"的放宽路径**——该入口对变宽方向拒绝并给固定提示"v1 不支持放宽可见范围，如需放宽请重新提交"。要更宽的可见范围，只能**重新提交一个版本**并在提交表单里选择目标范围（可见范围在更新版本时同样可改，与技能侧一致）；v1 **不为可见范围单设审核主题**，"放宽走审核"属后续版本议题。
  - 任一变更（含随新版本提交发生的变更）都触发索引重建并写审计（§8.6、§9）。
- **Git 来源下只有一个输入框：仓库地址（必填）。禁止出现子目录输入框，也禁止填分支 / tag / commit / 任何凭据。** 一个插件一个仓库，插件包必须位于**仓库根目录**——用户不提供任何"包在哪里"的信息，位置由规范决定、不是用户选项；凭据由平台配置，版本取自包内声明，分支取仓库默认分支的最新提交。仓库不符合规范时按 §6.4 第 6 条固定文案报错，**不提供让用户填路径绕过的入口**。
- **npm 来源下表单里没有版本输入框，禁止输入版本**（可 scoped 的包名是唯一来源参数）；分支 / tag / commit / 凭据同样不填。服务端查 registry 取最新非预发布版本，用户不指定、也不能覆盖；**任何途径传入版本都不受理**（产品红线，前端删输入框不够）。
- 页面必须提示："标题、简介、图标取自包内声明；如需修改请更新包后重新提交。"命名空间与来源提交后不可改；**分类与可见范围上架后可改**（§8.3、本小节）。
- **图标只取包内声明的图标字段**（按实际字节类型存为 SVG / PNG / JPEG / WebP），缺失用首字母占位；**不抓 README 首图、不做 data URL 内联**。

### 6.4 提交前校验（不通过当场拒绝并说明原因）

1. `package.json` 可解析，包名合法（含 scoped），版本是精确 SemVer；包未声明为私有；`engines.dsh` 若声明必须是合法版本范围。
2. **必须是 DSH 插件**：声明了 `dsh.bundle`（或等价 `dsh` 声明）才允许提交；缺失即**拒绝**，文案"这不是 DSH 插件：缺少 `dsh.bundle` 声明，装进 DSH 也不会生效"。
3. **包名全站唯一**：已被任何空间收录即当场提示"已被某空间收录"（§8.5）；**同一插件下版本不重复**。
4. **不接受登记已在镜像中的包**：镜像中同 `name@version` 已存在则拒绝，提示"该版本已存在，请改用新的版本号"。**同一 `name@version` 重复提交命中的是这一条，但下一步按来源分流**：
   - **Git**：同一仓库重复提交、默认分支没推进且包内版本号没改 → "**该版本已存在，请先在仓库中升级版本号再提交**"（作者有仓库可改）。
   - **npm**：版本由服务端取最新非预发布版本并在提交时冻结；latest 未变且该 `name@version` 已存在 → **409 拒绝**，固定文案"**该版本已存在，请先在上游 npm 发布新版本后重新提交**"。**不得沿用 Git 的"先在仓库中升级版本号"文案**——npm 用户没有仓库可改。
   两种来源都必须写明下一步，否则作者会反复点提交并以为系统坏了。
5. **包体边界**：zip 解压后不超过 50 MiB、文件数不超过 2000，不含路径穿越、符号链接、`.git` 目录；图标不超过 32 KiB 且为 SVG / PNG / JPEG / WebP 之一。
6. **Git 来源**：仓库地址接受 `https://host/group/repo` 与 `git@host:group/repo.git` 两种写法（内部归一），**用户不填分支、tag、commit，禁止填子目录**；校验三件事——① 地址能被解析；② **地址在平台允许范围内**，不在范围内当场拒绝并提示联系管理员；③ 能读到**默认分支与最新提交**，读不到则按类型分别提示（**地址不可达 / 无权限 / 仓库不存在**），不得笼统报"拉取失败"。**凭据由平台配置，用户不填任何凭据**（不得出现"把你的凭据贴进来"的表单，这是产品红线）。**仓库结构校验（一个插件一个仓库）**：插件包必须位于**仓库根目录**——根目录须存在 `package.json` 且声明 `dsh.bundle`（或等价 `dsh` 声明）；不符合一律按固定文案报错："**仓库根目录必须包含含 DSH 插件声明的 package.json（一个插件一个仓库），请按规范调整仓库结构后重新提交**"，**不提供任何让用户填路径绕过的入口**。

**npm 来源的提交前校验**：包名合法（可 scoped，形如 `name` / `@scope/name`）；服务端查询 registry 的 `latest` dist-tag，取**最新非预发布版本**（跳过 prerelease），**不提供任何让用户指定或覆盖版本的入口**；取不到时按类型分别提示——**包名不存在 / 无权限 / registry 不可达 / 只有预发布版本**，不得笼统报"拉取失败"。解析出的版本即该次提交冻结的版本（§6.6）。

### 6.5 异步受理与进度（链路顺序：扫描 → 审核（如需）→ 发布 → 上架）

**提交不同步返回扫描结论。** 提交后立即进入"已受理"，页面展示阶段进度并自动轮询，可离开、稍后回到「我的插件」按提交维度看进度。阶段（用户看到的中文，按序推进）：

**排队中**（已受理，含失败后的自动重试等待）→ **准备安装包**（下载 / 解包 / 整理成将要分发的包）→ **正在进行能力披露**（静态扫描）→ **等待审核**（仅团队空间；审核人看到完整报告作参考）→ **上架中**（对外提供安装所需的动作；不同来源耗时不同，**文案不解释差异**）→ **已上架**（进公共索引）/ **仅命名空间** / **私有** / **已通过（仅空间内可见）**（后三档均不进公共索引）——终态文案按 §8.4 的三档判定，不按"空间是否公开"猜。免审的个人空间不出现"等待审核"，**扫描通过即进入上架**。

- **审核在前，发布在后（这是 v2.8 的关键变化）**：团队空间待审的版本**尚未上架**——不进插件市场、不进索引，对非成员不存在，任何人（含知道包名的人）都装不到。审核页必须写明"**该版本尚未上架，通过后才会进入插件市场与索引**"，并展示内容指纹，供审核人按"通过即会被安装"来做判断。**审核页不得出现平台内部发布动作的说法**：不写平台把包放到了哪里、不写任何内部存储或分发通道，页面上只有"已上架 / 未上架"这一个维度。
- **审核页的包内文件浏览（团队空间审核的必要条件，不是可选增强）**：静态扫描允许漏判（§13 R4 已承认"未检出 ≠ 无风险"），所以审核人必须**自己能看到代码**；否则"审核"会退化成"看一眼扫描结论点通过"，团队空间的审核闸门就是装饰。审核页在插件审核字段块之下提供**包内文件浏览**：
  1. **必须具备**：审核人能看到该次提交的**包内文件清单（目录树 + 每个文件的大小）**与**单个文件的文本内容**，用于人工审查代码。清单**必须按目录层级分层展示、目录节点可折叠 / 展开**：目录节点显示"文件数 + 合计大小"，文件节点显示大小与类型；**禁止把全部文件平铺成一列完整路径**（32 个文件平铺就不可读，深目录看不出结构）。审核页必须**直接**给出清单与文本预览，不能只留"下载原始包、自己解压再看"这一条路。
  2. **数据来源必须是这次提交的待审暂存包**：审核发生在对外发布之前，公开入口还没有这个版本；展示的内容**必须与审核页展示的内容指纹 sha512 是同一份字节**。**不得**从上游 npm 或 Git 仓库重新拉取——那会看到另一份内容，"审的"与"发的"就不再是同一份东西（与 §6.6 的版本冻结同一条原则）。
  3. **只读、不执行（红线）**：预览一律以纯文本展示，**任何包内文件都不得在审核页被浏览器当作可执行内容渲染**——不渲染包内 HTML / SVG，不执行包内 JS，不把包内资源加载为页面内容。恶意插件不得借审核页攻击审核人。
  4. **二进制与超大文件**：二进制文件（图片 / 字体 / 压缩包等）**不展示内容**，只展示类型与大小，选中时提示"二进制文件不预览"；**单个文本文件超过 512 KiB 不内联预览**，提供「下载查看」——512 KiB（约 8000 行）兼顾人眼可读性与浏览器渲染开销：更小的内联看，更大的直接下载审。
  5. **敏感文件名提示**：清单中出现 `.env`、`*.pem`、`*.key`、`id_rsa` 一类文件时给出**视觉标记**（提示审核人重点看），但**不阻止查看、不阻断审核**——审核人就是要看这些文件。
  6. **权限**：与 §9 矩阵「审核插件版本（团队空间）」**完全一致**——**只有该空间的空间管理员**能浏览；平台管理员（`SKILL_ADMIN` / `SUPER_ADMIN`）**不在审核人之列**，不得据此条获得文件读取权限（他们查看扫描报告走矩阵「查看完整扫描报告与证据」那一行，与包内文件浏览是两件事）。非空间成员一律 **403**，不泄漏他人空间的提交与文件清单。**作者本人可看自己提交的包内文件**（那是他自己的包）。
  7. **审计**：审核人**打开包内文件浏览**、**查看单个文件**、**下载原始包或单文件**都必须写审计（谁、何时、哪个提交、看了什么，§9）。这是"审核确实做过人工检查"的唯一证据链。
  8. **边界不变**：文件浏览是**辅助手段**，不改变审核依据仍是"扫描报告 + 人工判断"；不因为"能看代码"就承诺"审过 = 安全"——对外表述仍只有四种（§7.1），禁止"已人工审核安全"一类措辞。
  9. **暂存包保留**：**审核期内暂存包必须可读**；审核结束后（通过并上架成功 / 拒绝）暂存包**至少保留 90 天**供回溯与审计取证，之后按现有保留策略处理。不得因"审核已结束"就清包，否则历史审核无法回溯"当时审的到底是哪份内容"。
- **发布失败（只有 zip / 文件夹来源会走到这一步；两种空间各有归属态）**：个人空间 → 版本停在**待发布**（可见、可重试）；团队空间 → 停在「**已通过审核，等待发布**」（可见、可重试）。两态都**不产生可安装制品**、不进索引，作者在「我的插件」看到脱敏原因并可重试；**重试不改变审核结论**，审核通过不会因发布失败而回滚。**npm 与 Git 来源没有这一步**——它们本来就有可分发位置，审核通过即上架（§6.2）。
- **审核拒绝 = 不发布**：该次提交**不产生任何制品**、不建可安装版本、不进索引；版本置为未通过，作者看到拒绝理由并可改包重提。**没有"撤包"这个动作**——拒绝发生在对外发布之前，不存在需要考虑撤回的制品。
- **不做时效性重扫**：审核使用**提交时**的扫描报告，不因报告"超过 N 天"自动重扫；报告页始终显示生成时间，审核人可据此要求管理员手动重扫（§7.4）。
- 失败终态必须可解释、可重试：**有红线**（附证据与"改包重提"指引）、**扫描未完成，可重试**、**发布失败（待发布，仅 zip / 文件夹来源）**、**已通过审核，等待发布（发布失败，可重试）**、**审核未通过**（附理由，不产生任何制品）、**包信息与声明不一致**。
- 页面明示"索引通常在 1 分钟内生效"（§8.6）。轮询期间禁止重复提交同一包同版本。

### 6.6 失败、回滚与重提

- **有红线**：**不建版本、不产生任何制品、不进索引**，但**本次提交与其扫描结论、报告保留**（供追溯与放行）；用户看到红线清单与证据，按"改包重提"处理；管理员可按 §7.4 对本次提交的该结论确认风险，放行后本次提交继续走后续流程。
- **扫描失败**：一律视为未通过（绝不静默当作"未检出"），提示可重试；服务恢复后重试成功即可。
- **发布失败**（仅 zip / 文件夹来源）：个人空间停"待发布"、团队空间停「已通过审核，等待发布」，均可重试（§6.5），可见性按 §8.4 口径（非成员不可见、成员可见失败原因与重试入口）；**审核结论不因发布失败回滚**。**审核未通过**：不产生任何制品、不进索引，版本置为未通过，作者看到理由并可重新提交。
- 同包同版本内容不可覆盖：改代码必须发新版本。
- **同一仓库连续提交**：版本内容固定为**提交那一刻**默认分支的最新提交；之后仓库继续提交**不影响已上架版本**。若默认分支没推进、包内版本号也没改，会按"同一版本已存在"拒绝——提示"**该版本已存在，请先在仓库中升级版本号再提交**"，这是预期行为，不是系统故障（§6.4 第 4 条）。
- **npm 来源版本在提交那一刻冻结（产品规则）**：用户只填包名，服务端解析出的**最新非预发布版本**写入该次提交的快照；之后的扫描、审核、发布、上架**全程复用这个已冻结版本**，**不得在后续阶段重新解析 latest**。理由：npm 的 `latest` 会移动，提交时是 1.0.0、审核时上游发了 1.0.1，若重新解析就会"审的是 A、发的是 B"，破坏"扫的就是发的"内容指纹断言。**上游 npm 之后发新版本不影响已上架版本**；要上新版必须**重新提交**（届时服务端会取到新的 latest）。重复提交且 latest 未变、该 `name@version` 已存在 → 409 拒绝并按 §6.4 第 4 条的 npm 专属文案提示。

## 7. 内容政策与扫描披露（用户可见部分）

### 7.1 定位与边界（产品政策，不可协商）

扫描器为 **`dsh-trust-check`**（MIT，静态分析），做的是**静态能力披露**：把插件会碰什么、注入了什么、来源是否可核对摊开，每条附 `文件:行号` 与原文片段。**它不是杀毒、不做安全背书**：`未检出` 只表示"本次静态扫描没看到"。因此：

- 本站**任何位置**（页面、文档、提示词、通知、运营物料）禁止表述为"安全 / 已认证 / 无风险 / 通过安全检测"；对外表述只有四种：**未检出风险信号 / 需确认 / 有红线 / 扫描失败**。
- 详情页必须常驻免责说明与已知局限（照抄工具语义，不改写）：只扫给定目录、不展开依赖树、运行时拼接的 `import` / 字符串拼 URL / 混淆的 `eval` 可能绕过规则表、扫描发生在安装前（无法阻止安装脚本在其他客户端执行）、排序分只是参考不是裁决依据。

### 7.2 四种裁决与用户表述

| 裁决 | 条件 | 用户看到什么 / 能不能继续 |
|---|---|---|
| **有红线** | 命中任一红线 | 默认**挡住**：不建版本、不产生任何制品、不进索引；提交者看到清单与证据。本次提交与其报告保留，管理员可对**本次提交的该结论**确认风险（§7.4），放行后继续 |
| **需确认** | 无红线但有特权能力，或注入了宿主配置 / 系统提示词 | 允许继续；详情页**必须**展示能力清单，卡片与列表带"需确认"徽标 |
| **未检出风险信号** | 无红线、无特权能力 | 允许继续；详情页仍必须展示披露区块，不得隐藏 |
| **扫描失败** | 报告不可解析、版本不识别、超时、进程失败 | 一律按未通过处理（fail closed），可重试；不存在"扫描服务不可用就放行"的旁路 |

只按"红线 + 能力"判断，不看排序分。安装脚本红线特别说明：本站安装文档强制 `--ignore-scripts`，但用户可能用其他客户端或手工安装，故仍默认拦截，确需收录由管理员放行。

### 7.3 展示位置与文案原则

- **详情页**：裁决 → 能力清单 → 红线（中文固定文案 + 证据折叠）→ 工作区外路径 / 密钥触摸 / 字面量去向（折叠）→ 扫描器版本与时间 → 免责与已知局限。
- **卡片 / 列表**：只在"需确认"与"有红线"上显示徽标；"未检出风险信号"不带徽标（详情页仍展示区块）。**审核页**看完整报告与证据，并可浏览本次提交的**包内文件清单与文本内容**（§6.5），作为参考而非替代判断；**安装文档**附一行摘要供 Agent 转述。**索引文件不含任何披露字段**：官方协议没这些字段，多写会让整份索引被拒。
- 文案原则：能力与红线一律用工具冻结的固定中文短语（如"会执行系统命令""会读取本机文件""会访问网络""安装时会执行脚本""覆盖或禁用了 DSH 核心 bundle""代码中检出：读取凭据的值，且有网络访问"），**不自造措辞、不扩大工具没观测到的范围**；未知能力或红线原样显示英文，不报错。完整取值见 design.md 文案清单。

### 7.4 放行、申诉与重新扫描

- **放行对象是"本次提交的该结论"**，不是某个版本（红线版本根本不存在）：仅平台管理员（`SKILL_ADMIN` / `SUPER_ADMIN`）可操作，**必须填理由**、留痕、可撤销；放行后该次提交继续走"审核 → 发布 → 上架"。放行内容变更后失效（必须重新判定），撤销放行时若版本已上架则自动下架。
- **撤销放行必须通知，不能静默下架**：撤销导致自动下架时，站内通知**插件作者**与**该次放行的审核人**（即当时判定的操作人），说明撤销原因（含新结论与证据指向）与重新提交 / 重新判定的路径；沿用现有站内通知渠道，**不新增通道**。通知与撤销动作同一次写入审计。
- **放行后的展示**：详情页对所有人显示"管理员已确认风险"+ 理由摘要，**不得**显示为"通过"；审计记录版本 / 内容指纹、红线 code、操作人、理由。
- **重新扫描**：空间管理员 / 平台管理员可对某版本发起，有频率限制；每次新增一份报告、历史不覆盖（必须能回答"当时为什么放行 / 拦截"）。
- **扫描器升级后的重扫**：后台批量重扫、不改版本状态；若结论由"未检出"变"有红线"，**自动下架并告警**，同时产出一份**差异清单**（版本、旧裁决、新裁决、命中 code、处理入口）在告警里给出链接，列表页支持按"漂移命中"筛选——**不做批量操作**，但必须能一眼看全。
- **误报反馈**：报告里提供"这是误报"入口，带工具版本与证据指向上游；本站不自行改判规则表，只做上面的放行。

### 7.5 与技能扫描的边界

技能侧与插件侧是两套扫描、两套语义：**不得**用技能侧的"是否安全"口径解释插件结论，**不得**把插件能力清单混入技能的审计结论，也**不得**复用技能侧的扫描中 / 扫描失败版本状态机。插件扫描是提交链路上的一环，失败即提交不通过（可重试）。

## 8. 上架与分发规则

### 8.1 上架闸门跟随命名空间策略

- **个人空间**：免审——扫描通过即上架（zip / 文件夹来源需先发布成功）。**团队空间**：扫描通过后**先审核**，审核通过才对外提供安装，**上架成功才进索引**；**审核拒绝即不发布**（无制品、不进索引，§6.1、§6.5）。
- 上架前做**一致性复核**：最新扫描为"有红线"且未放行、或最近一次扫描失败，不得上架；报告用提交时那一份，**不做时效性自动重扫**（审核人可要求手动重扫）。下架、恢复、撤版、删除、释放包名、放行均写审计（§9）。

### 8.2 收录条件（缺一不可）

- 插件状态为**已上架**，未被下架、未在黑名单；所属命名空间为**公开空间**，**且插件可见范围为 `PUBLIC`**（`NAMESPACE_ONLY` / `PRIVATE` 不进公共索引，见 §8.4）。
- 至少有一个已上架版本，且该版本**有可分发位置**（内部 npm 镜像里已有该包的该版本，或该版本的 Git 仓库地址 + 提交号可用，§8.6）、分发来源可解析、裁决不为"有红线"（已放行的除外）。
- 包名在全站唯一（§8.5）。

### 8.3 分类：9 类，插件归属一个分类

| 分类 | 中文 | English | 分类 | 中文 | English |
|---|---|---|---|---|---|
| `agent` | 智能体 | Agents | `devtools` | 开发工具 | Developer Tools |
| `ui` | 界面 | Interface | `search-knowledge` | 搜索与知识 | Search & Knowledge |
| `memory` | 记忆 | Memory | `data` | 数据分析 | Data Analysis |
| `communication` | 通信 | Communication | `security` | 安全 | Security |
| `other` | 其他 | Other | | | |

归属规则：每个插件**有且只有一个**分类；提交时由提交者从 9 类中必选 1；上架后可由空间管理员或插件作者修改（触发索引重建、写审计）；分类集合固定 9 类、不随数据增删，某分类下 0 个插件时市场页仍展示该筛选项。

### 8.4 可见性与状态文案

可见性由**空间是否公开**与**插件可见范围**（§6.3 三档）共同决定，按序命中下表第一行：

| 空间 | 可见范围 | 是否进公共索引 | 谁能看到 | 状态文案 |
|---|---|---|---|---|
| 公开空间 | `PUBLIC` | 进 | 匿名 + 站内所有用户；DSH 用户在「发现」页可搜到 | **已上架** |
| 公开空间 | `NAMESPACE_ONLY` | **不进** | 仅该空间成员站内可见，非成员按未上架处理 | **仅命名空间** |
| 公开空间 / 私有空间 | `PRIVATE` | **不进** | 仅作者本人；空间 OWNER / ADMIN 与超级管理员可按治理规则访问 | **私有** |
| 私有空间（含个人空间未公开） | `PUBLIC` / `NAMESPACE_ONLY` | **不进** | 仅空间成员与管理角色 | **已通过（仅空间内可见）** |

- **状态文案必须按上表判定，不能只按"空间是否公开"猜**：`NAMESPACE_ONLY` 与 `PRIVATE` 在公开空间下同样是"上架但不进索引"，不能显示"已上架"。
- **两档非公开可见范围都要给稳定说明句**，避免作者以为"上架了同事在 DSH 就能搜到"：`NAMESPACE_ONLY` → 列表与详情页写"该插件可见范围为仅命名空间，不会出现在公共索引中，空间成员可在站内查看"；`PRIVATE` → "该插件可见范围为私有，仅作者本人可见，不会出现在公共索引中"。`PUBLIC` 落在私有空间时沿用原有说明句"该插件所属空间为私有，不会出现在公共索引中"。
- **不进索引的分发路径**：站内为该范围内的可见者提供手工安装命令（`dsh plugin --profile <profile> add {name}@{version} --ignore-scripts` + 该版本的 registry 地址），不依赖索引。
- **待发布 / 已通过审核，等待发布**（发布失败的两个态，仅 zip / 文件夹来源会走到）：**对非成员按未上架处理**——该版本的详情页返回 **403**、安装文档返回 **404**（对外语义同为"不存在"、不泄漏存在性，两套状态码各管一侧：页面给人、文档给 DSH 客户端）、不返回任何内容，不进索引；插件若无任何已上架版本，其对非成员的详情页同样返回 403。**空间成员可见**，并在「我的插件」与详情页看到脱敏失败原因与重试入口（提交侧流程见 §6.6）。
- **黑名单（全站禁止上架）对存量版本同样生效**：加入黑名单**即刻下架**，下一轮索引重建即从索引剔除，安装文档与该插件的全部路径 404；存量包文件**不删除**（保留取证）但**永不再进索引**；解除黑名单也不自动恢复上架，须重新执行「恢复上架」（§9）。
- **非成员访问**：私有空间的插件详情，以及 `NAMESPACE_ONLY` 插件对非该空间成员的访问，一律按"不存在"处理（403，不泄漏存在性）；`PRIVATE` 对非作者按同一规则处理。
- 下架即从索引消失，恢复后按上表重新判定是否回到索引（可见范围非 `PUBLIC` 的插件恢复上架后仍不进索引）。

### 8.5 包名归属与释放

- 一个 npm 包名只能被一个空间收录；提交时即校验，**三种情形都当场拒绝，但下一步不同**：① 该包名已被限制（黑名单）→"该包名已被限制，请联系管理员"；② 该包名已下架但名额未释放（原插件已软删）→"该包名已被下架，名额未释放"，申诉路径为联系原空间或平台管理员释放；③ 已被其他空间收录 →"已被 X 空间收录"，联系该空间或平台管理员。已上架包名不会被后提交者覆盖。
- 索引生成期再加一道断言：发现重复即视为构建失败并告警，**不做**"静默取上架时间最早者"的降级。
- **下架 / 撤版不释放包名**：插件仍占住该名称，避免"同名不同内容"在索引里互换。
- **撤空即自动下架**：撤掉最后一个可上架版本时，插件**自动转为未上架**，作者在「我的插件」看到"已无可安装版本"，恢复上架必须先有至少一个可上架版本。不允许"已上架但无可安装版本"的状态（索引生成也会因此失败）。
- **换归属只有一条路**：先由空间管理员或作者**删除**该插件（软删，保留审计与安装包），再由 `SUPER_ADMIN` **释放包名**；释放后旧地址（详情页、安装文档、图标）返回 404，该插件的全部版本立即从索引消失，包名可被其他空间重新提交。删除与释放都必须填理由并写审计。

### 8.6 索引源对外承诺（用户可感知）

- 匿名可添加、可被 DSH 直接拉取，**不会跳转**，不因登录态或审核系统故障而不可用；子路径部署下索引里的图标、详情页链接、安装文档地址都必须可正确打开。生成失败时**保留上一版索引继续服务**，宁可短暂陈旧，不给 DSH 一个坏文件或错误页。
- 状态变化后**通常在 1 分钟内**生效；批量变更（如扫描器升级重扫）可能更久，界面文案按"通常"表述。连续变化只重建一次（合并调度），不做逐事件重建。
- **每个条目的分发来源与用户的上传方式无关**：生成索引时**逐个已上架版本**判定——**内部 npm 镜像里已有该包的该版本，就按 npm 写**（镜像地址 + 版本）；**没有才退回该版本的 Git 仓库地址 + 提交号**；**两者都不存在的版本不满足收录条件、不得上架**（§8.2）。索引只收录满足 §8.2 的版本——可见范围为 `NAMESPACE_ONLY` / `PRIVATE` 的插件不出现在索引中（§8.4）。这样同一份内容无论来自 npm、Git 还是 zip / 文件夹，用户拿到的安装路径一致；**"上传方式"彻底成为内部实现，不进索引、不出现在详情页**——详情页「分发来源」显示的是这个判定结果，不是用户当初选了哪种上传方式。

| 加入 / 移出黑名单（全站禁止上架） | — | — | — | ✓（`SUPER_ADMIN`） |

- **可见性口径**：本站"能看见谁"由 §8.4 的可见范围与空间公开状态决定；本矩阵只规定"谁有权做这个动作"，不改变可见范围。
- **审计覆盖**：提交、审核决定（通过 / 拒绝 + 理由）、**审核人查看 / 下载包内文件**（打开包内文件浏览、查看单个文件、下载原始包或单文件；记谁、何时、哪个提交、看了/下了什么）、**发布产物**（仅 zip / 文件夹来源；包名 / 版本 / 内容指纹 / 目标源 / 结果）、**发布重试**（次数与结果，含「已通过审核，等待发布」期间的重试）、上架与**恢复上架**（理由、当时最新裁决）、下架、撤版、**改分类**（旧值 → 新值）、**改可见范围**（旧值 → 新值、生效时点）、删除与**释放包名**、**黑名单**（理由、影响范围）、红线放行 / 撤销、重新扫描、扫描器升级导致的自动下架。必须写清：谁、何时、哪个对象、理由。
- **黑名单的范围是全站且含存量**：加入黑名单即刻下架，下一轮索引重建即剔除，安装文档与该插件全部路径 404；存量包文件保留取证、永不再进索引；解除后须重新「恢复上架」，不自动恢复（细则见 §8.4）。
- **软删**：已发布版本保留安装包与扫描报告供追溯，不可被同名同版本覆盖。
- 非空间成员访问提交页或空间插件列表 → **一律 403 拒绝访问**（不显示空态），**不得泄漏**他人空间插件清单。

## 10. 统计口径

- 只统计两项事件：**浏览**（详情页曝光）只落库统计，**v1 不提供任何界面展示**（运营如需查看走报表/查库），不向作者开放；**v1 唯一对外展示的计数是详情页的「复制提示词次数」**。两项都按来源（匿名以出口地址近似）去重到"同一来源同一天同一插件同一事件只计 1 次"。
- **对外只展示 `复制提示词次数`**，且只在详情页展示，并标注"按来源去重，内网共用出口时会偏低，仅供参考"；**市场卡片不展示任何计数**——复制动作只发生在详情页，卡片上的数字只能反映"点进来的人"，用来衡量市场吸引力是错的。
- **不叫"安装量 / 用户数"**：站内无法确认用户在 DSH 内是否安装成功（拉包还含 CI 噪声），本期不接分发端指标。
- **没有"下载"统计**：站内不提供 tarball 下载，也不统计任何下载行为。

## 11. 验收标准（产品级）

验证方式标记：`[自动]` 可脚本 / 接口断言 ｜ `[人工]` 人工走查页面与交互 ｜ `[真机]` 必须在真实 DSH 客户端完成。
**A. 索引源与市场页**
1. `[真机]` 上架 1 个 npm 来源插件后，用户在 DSH 打开自定义插件索引并添加本站索引地址，「发现」页能看到该插件卡片与推荐版本。
2. `[人工]` `/plugins` 自上而下只有「索引源」「插件列表」两模块；索引地址可复制并有成功态；空索引时提示"暂无已上架插件"并给"成为第一个收录的插件"入口；关键词、9 类筛选、排序、加载更多均生效，无结果给"清空筛选"。
3. `[自动 + 真机]` 索引文件可匿名拉取、不跳转、格式符合官方协议；子路径部署下图标与详情链接可正常打开；图标扩展名与实际类型一致（PNG 图标不会 404）；**每个条目的分发来源与上传方式无关**——镜像里已有该包该版本写 npm，缺失才写 git 地址 + 提交号，两者都无则该版本不得上架。
4. `[人工]` 卡片上不出现任何计数（浏览数、复制次数），也不出现"复制提示词"按钮。
**B. 详情页与提示词**
5. `[自动]` 详情页**没有任何选版本控件**（无下拉 / 单选 / 输入框 / 逐版本复制或安装入口），只有一个只读的当前最新版本号与一个「复制提示词」；复制得到的提示词（`请按照 {站点地址}/dsh/install/{ns}/{slug}/{version}.md 安装 DSH 插件 {npm 包名}@{version}。`）里两次出现的版本必须**等于复制那一刻的最新已上架版本**，安装文档内容与该版本一致；复制后 `复制提示词次数` +1 并显示"仅供参考"说明。
6. `[自动]` 无版本段的旧路径 `/dsh/install/{ns}/{slug}.md` 仍可用，内容为**当前最新已上架版本**，不 404。
7. `[自动]` 安装文档含 7 段：包名、精确版本、`engines.dsh`、Profile 占位、`--ignore-scripts`、校验与卸载命令、匿名只读说明；全文不含任何 Token。
**C. 提交（异步链路）**
8. `[人工]` 提交合法 npm 包或 zip 后立即进入"排队中"，进度按 排队中 → 准备安装包 → 正在进行能力披露 → **等待审核**（团队空间）→ **上架中** → **终态** 推进（免审的个人空间不出现"等待审核"）；**终态有四个文案，按 §8.4 四行判定表取，不能只写「已上架」**——公开空间 + `PUBLIC` →「已上架」（**只有这一档进公共索引**）、公开空间 + `NAMESPACE_ONLY` →「仅命名空间」、任一空间 + `PRIVATE` →「私有」、私有空间 + `PUBLIC` / `NAMESPACE_ONLY` →「已通过（仅空间内可见）」；走查时改用 `NAMESPACE_ONLY` 插件应看到「仅命名空间」而非「已上架」；期间可离开，在「我的插件」按提交维度看到阶段与失败原因。
9. `[人工]` 内网 Git 提交后详情页显示 git 来源，提交号与仓库默认分支最新提交一致；选文件夹提交与上传同一目录 zip 结果一致，浏览器不支持选目录时提示改用 zip。
10. `[自动]` 缺 `package.json`、缺 `dsh.bundle` 声明、含路径穿越的包 → 当场拒绝并给出具体原因，索引不变。
11. `[自动]` 重复提交同包同版本 → 当场提示版本已存在；包名冲突三分支都当场拒绝且提示不同——已被他空间收录 →"已被 X 空间收录"、已下架未释放 →"已被下架，名额未释放"、黑名单 →"已被限制，请联系管理员"；该 `name@version` 已在镜像中存在 → Git 来源提示"请改用新的版本号"，**npm 来源 → 409 拒绝并固定提示"该版本已存在，请先在上游 npm 发布新版本后重新提交"**（不沿用 Git 的"先在仓库中升级版本号"）。**npm 路径走查**：表单无版本输入框、任何途径传入版本都不受理；版本取最新非预发布版本并在提交时冻结，latest 未变且该 `name@version` 已存在即按重复拒绝。
12. `[自动]` 有红线的包 → 终态"有红线"，展示证据；**不产生版本、不产生任何制品、索引不变**，但该次提交与扫描报告可在站内查到。
**D. 导航与入口**
13. `[人工]` 顶部导航为 `首页 / 技能市场 / 插件市场 / 技能套件 / 控制台`（插件市场在技能市场之后）且无「发布」；页脚发布链接仍可达。
14. `[人工]` 登录用户在 `/search` 页头看到「我的技能」+「发布技能」；未登录用户在 `/plugins` 页头看不到「我的插件」与「提交插件」。
15. `[人工]` 控制台侧栏在「我的技能」后有「我的插件」且高亮正确，概览区同时有「我的插件」卡；从「我的技能」触发更新版本仍能跳转发布页并完成发布（回归未被导航改动破坏）。
**E. 治理**
16. `[自动 + 人工]` 团队空间：扫描通过后**先审核**，审核通过才对外提供安装，**发布成功才进索引**（且发布成功后仍须**可见范围为 `PUBLIC` 且空间公开**才真的进索引，否则按 §8.4 显示「仅命名空间」/「私有」/「已通过（仅空间内可见）」）；**审核拒绝不进索引、不产生任何制品**（该版本谁都装不到），作者看到理由，审计含审核结论与理由。**npm 路径**：该版本为提交时冻结的最新非预发布版本，审核与发布全程复用、不重新解析 latest。**审核页文案断言**：全页只允许"已上架 / 未上架 / 发布 / 上架"这一种口径，**不得出现任何平台内部动作或内部分发通道的说法**，固定文案为"**该版本尚未上架，通过后才会进入插件市场与索引**"。**人工走查（包内文件浏览）**：审核页可浏览本次提交的**包内文件清单（目录树 + 大小）与文本内容**，**清单必须按目录层级展开、目录节点可折叠、目录节点显示文件数与合计大小**，**不得把全部文件平铺成一列完整路径**；且内容与页面展示的 **sha512 指纹为同一份字节**（不是从上游 npm / Git 仓库另拉的一份）；二进制文件（如图片）不预览内容、只显示类型与大小；预览区**不渲染任何包内 HTML / SVG、不执行包内 JS**；单文件超 512 KiB 给「下载查看」（阈值兼顾可读性与预览渲染开销）；`.env` / `*.pem` 一类有敏感标记但仍可打开；非空间成员访问 403，作者本人可看自己提交；查看与下载均产生审计。
17. `[自动 + 人工]` **发布失败（仅 zip / 文件夹来源会走到这一步）** → 个人空间停"待发布"、团队空间停「已通过审核，等待发布」，两态都**没有可安装制品、不进索引**、作者可见脱敏原因并可重试；重试成功后才上架，且**审核结论不因发布失败回滚**；**npm 与 Git 来源不经这一步，审核通过即上架**。审核页必须写明"**该版本尚未上架，通过后才会进入插件市场与索引**"并展示内容指纹。
18. `[人工]` 命名空间插件 tab 顺序为 `技能 / 插件 / 成员 / 审核 / 设置`；列表含"索引状态"列（已收录 / 待重建 / 未收录：空间为私有 / 未收录：可见范围非公开 / 未收录：最新版本裁决为有红线 / 未收录：无已上架版本），可下架、恢复、撤版、改分类、**改可见范围（仅缩窄立即生效；放宽被拒并给固定文案）**。
19. `[自动]` 下架 → 通常在 1 分钟内从索引消失且审计有记录，恢复后重新进入；撤版 → 该版本退出索引、默认版本回退到上一个已上架版本、列表排序不变；**撤掉最后一个可上架版本 → 插件自动转为未上架**，站内提示"已无可安装版本"，无已上架版本时不允许执行恢复上架。
20. `[自动]` 删除后包名仍被占用；`SUPER_ADMIN` 释放包名后旧地址 404、全部版本从索引消失、可被其他空间重新提交；删除与释放均有审计。
21. `[自动]` 非空间成员访问提交页或空间插件列表 → **403**（不显示空态），不泄漏他人空间清单。
**F. 统计**
22. `[自动]` 对外只在详情页展示 `复制提示词次数`；同一来源同日重复复制只计 1 次；全站无"安装量 / 下载量"字样，卡片无任何计数。
**G. 内容披露与扫描**
23. `[自动]` 未检出风险的插件详情页仍展示披露区块与免责说明；全站任意位置都不出现"安全 / 已认证 / 无风险 / 通过安全检测"。
24. `[人工]` 含网络与文件写入能力的插件 → "需确认"：允许继续，详情页列出两条能力，卡片带"需确认"徽标。
25. `[自动]` 声明安装脚本的包 → 终态"有红线"，展示中文固定文案与 `文件:行号` 证据；扫描超时或报告不可解析 → 终态"扫描未完成，可重试"，不会静默变成"未检出"。
26. `[自动]` 管理员对"某次提交的红线结论"放行并填理由 → 该次提交继续走审核与发布直至上架，详情页显示"管理员已确认风险"+ 理由摘要；撤销放行后已上架版本自动下架。
27. `[自动]` 扫描器升级重扫使某版本由"未检出"变"有红线" → 该插件自动下架、从索引消失、告警附差异清单，列表可按漂移命中筛选。

**真机手工脚本（唯一真机门禁）**：记录 DSH 版本、profile 与执行人。步骤：① 打开 DSH「插件 → 实验性插件 → 自定义插件索引」，添加本站索引地址；② 从「发现」页点开该插件卡片进入站点详情页，复制提示词；③ Agent 按安装文档执行 `dsh plugin --profile <p> add {name}@{version} --ignore-scripts`。
**"装成功"的判据（三条全过才算通过，缺一不算）**：① 该插件出现在 DSH「发现」页的索引结果中；② `dsh plugin add` 退出码为 0；③ 该包与版本出现在 `dsh plugin --profile <p> list` 的输出中。构建、单测、截图都不能替代真机。脚本本体由架构师起草、产品维护上述判据、QA 执行并留证据。

全新域，一次性上线；分期只表示范围与出口条件，不代表灰度放量。

## 13. 风险与开放问题（产品侧）

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| R1 | 官方索引协议演进（当前为实验特性） | 索引可能被新版 DSH 拒绝，市场整体不可用 | 生成器版本化；发布前用官方校验库校验；生成失败保留上一版继续服务 |
| R2 | 单条数据不合规导致**整份索引被拒**，或更新后延迟窗口（提交成功 → DSH 可见） | 用户"加了索引源却什么都看不到"、以为失败并重复提交 | 生成期强校验 + 管理员告警 + 上线前真机脚本；页面明示"通常 1 分钟内生效"；重复提交有拦截 |
| R3 | 发布任意第三方代码到内部源 | 供应链风险 | 红线默认拦截在发布之前；团队空间**审核也拦在发布之前**（未通过的版本不会进入内部源，不存在"审核期就能被装到"）；安装包留存与内容指纹；放行必须留痕 |
| R4 | 静态扫描漏判被当成"无风险" | 用户误信、事故归因困难 | 禁用词政策；详情页常驻免责与已知局限；"未检出"不等于"无风险" |
| R5 | 误报阻塞正常内部插件 | 业务无法上架 | 管理员对该次提交的结论放行（留痕且页面可见）；误报反馈到上游 |
| R6 | 私有空间插件"上架了但同事搜不到" | 首次体验挫败 | 状态文案"已通过（仅空间内可见）"+ 稳定说明 + 站内手工安装命令 |
| R7 | 内部镜像不可用 | 上传型来源（zip / 文件夹）全部失败 | 已裁决强制匿名只读；镜像异常时提交停"待发布"或「已通过审核，等待发布」可重试，不产生半成品 |
| R8 | **审核依据的扫描报告可能过时数天**（已裁决不做时效性自动重扫） | 审核人可能用一个几天前的静态结论做今天的裁决 | **接受该风险**：报告页始终显示生成时间；作者重新提交或管理员手动重扫即可更新（§7.4）；界面在审核页把生成时间放在裁决旁边 |
| R9 | **审核通过后发布长期失败**，插件始终上不了架 | 作者以为"审过了就等于上线"，实际一直不可安装；审核结论悬空 | 自动重试 + 管理员手动重试入口 + 失败超阈值告警；作者在「我的插件」看到「已通过审核，等待发布」+ 脱敏原因 + 重试按钮；**审核结论不回滚**，恢复发布后直接上架 |
| R10 | **默认分支随时可能被推进** | 作者以为"仓库一提交，市场就更新"，实际已上架版本固定不变 | 版本内容固定为**提交那一刻**的默认分支最新提交，之后仓库再有提交不影响已上架版本；要上新版必须在包内**升级版本号**再提交（否则按"该版本已存在"拒绝并提示先升级版本号，§6.4 第 4 条、§6.6） |
| R11 | **npm `latest` 会移动**（上游随时可能发新版本，`latest` 指向另一版本） | 若后续阶段重新解析 latest，就会"**审的是旧版、发的是新版**"，破坏"扫的就是发的"内容指纹断言；或用户以为"上游一发版市场就更新"，实际已上架版本不变 | 版本在**提交那一刻冻结**（取最新非预发布版本写入该次提交快照）；扫描 / 审核 / 发布 / 上架**全程复用已冻结版本**，后续阶段**绝不重新解析 latest**；上游发版**不影响已上架版本**，要上新版必须**重新提交**（§6.4、§6.6）。重复提交且 latest 未变、该 `name@version` 已存在 → 409 拒绝并按 npm 专属文案提示 |
| R12 | **审核人可能只看几个文件就点"通过"**（给了看代码的手段，不等于会认真看） | "人工审核"退化为形式，出事后无法证明审核人到底看过什么；团队空间的审核闸门只剩仪式感 | 不把它当技术问题，用三条产品约束兜：① 审核页**必须**给文件清单 + 文本预览且只读不执行（§6.5），先消除"看不到"这个客观障碍；② **查看 / 下载包内文件全部写审计**（§9），形成"审核做过人工检查"的唯一证据链，事后可回溯；③ 拒绝**必须填理由**、审核结论写审计；同时**不对外承诺**"审过 = 安全"——对外仍只有四种裁决表述（§7.1），审核质量本身属组织管理问题，不通过文案包装掉 |
| R13 | **索引里的分发来源与实际能装到的那份不一致**；或镜像里明明已有该包的该版本却写了 git 地址 | 用户按索引安装时多走一条不稳定的路径（git 依赖仓库地址与提交号可用性），或装到与详情页承诺不同的那份，"索引写什么就装什么"的承诺落空 | 生成期**统一判定、优先镜像**：逐个已上架版本先查内部 npm 镜像，有该包该版本就写 npm，缺失才退回 git 地址 + 提交号；两者都无则**不得上架**（§8.2、§8.6）；同一份内容只写一个分发来源，不做双写、不按上传方式回填 |

**部署期未知项的好消息**：**内部源是否支持删除已发布版本，不再影响审核链路**——v2.8 把审核放在发布之前，审核拒绝时发布尚未发生，没有"撤包"这个动作，因此不必依赖内部源的删除能力（这曾是最大的部署期未知项）。内部源只要求可上传、可匿名只读。
