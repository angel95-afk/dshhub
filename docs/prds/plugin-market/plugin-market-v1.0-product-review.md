# PRD 研发视角评审：DSH 插件市场 v1.0

评审对象：`plugin-market-v1.0-prd.md`（v1.1，839 行）
交叉比对：`openspec/changes/add-plugin-market/design.md`（本人产出的技术设计）、仓库既有实现（`web/nginx.conf.template`、`server/`、`scanner/`）

**总体判断（三个最大风险）**

1. **提交链路的时序没有闭合**：`红线拒绝 → 不落库` 与 `管理员放行需要报告/版本` 直接冲突，放行功能在数据上不可达；同时"同步扫描"与"120s 硬超时 + 网关 60s"不可能同时成立。这两条决定了 P1 阶段就要返工。
2. **"动作"与"接口/状态"不成对**：下架、恢复上架、删除、撤版、黑名单在权限矩阵里都有，接口清单里一个都没有；而 §3.4 承诺的"下架 + 重新提交"迁移路径在 `package_name` 全站唯一下根本走不通。上线后运营会立刻卡住。
3. **对外契约有无法实现的自相矛盾**：安装提示词不带版本 + 安装文档路径不带版本段 + 版本列表每行要求"文档指向该版本"，同一 URL 无法表达多版本；索引图标写死 `.svg` 却允许 PNG/WebP。前者影响路由与索引结构，属于结构性问题而不是措辞问题。

## P0（会导致返工或上线后不可运营）

### R1 红线拒绝后没有可放行的对象：放行功能在数据上不可达

**现象**：§6.5（264 行）"命中红线或扫描失败即终止：不写私服、不落版本"；§10.3（621–626 行）命中红线的 422 响应里 `"reportId": null`；但 §7.2（307 行）与 §7.6（400 行）要求 `SKILL_ADMIN`/`SUPER_ADMIN` 对该版本"确认风险放行"。而 §9.3（548 行）把报告挂在 `plugin_version_id`（FK）上，`design.md:1038` 进一步把它定为 `NOT NULL`。
**为什么是问题**：放行动作需要绑定"某版本的某份报告 + 指纹"（§7.6 明确要求"绑定版本指纹"）。red 分支既不建 `plugin_version` 也不建 `plugin_scan_report`，因此没有任何行可以承载 `waived_by/waived_at/waive_reason`，也没有 `reportId` 可交给放行接口。我的设计里同样存在这个缺口：`design.md:567` 在 red 分支写 `saveScanReport(SUCCESS, RED)`，而报告表的外键 `NOT NULL` 指向不存在的版本，这条写库操作会直接失败。
**影响**：§16.27（790 行）这条验收无法通过；"误报阻塞正常内部插件"（R9）没有出口，唯一的实际做法是让作者改代码重发，而红线恰恰是"改代码不一定能改掉"的那类问题。返工范围横跨报告表结构、提交状态机、放行接口与详情页展示。
**建议**：让扫描报告挂在一个**一定存在**的主体上，二选一并在 PRD 写死：① 报告表改为可挂在 `plugin_submission` 上（red 时报告属于某次提交而非某个版本），放行 = 对"该 submission 的该指纹"放行，放行后允许本次提交跨过闸门继续；② 明确"red 不落版本"改为"red 落一个 REJECTED 版本用于承载报告与放行"，索引与私服仍不写入。推荐 ①，因为版本表一旦为拦截态留行，后续所有"版本存在即已发布"的隐含假设都要重新审一遍。
**归属**：产品规则（+技术补强）

### R2 同步扫描闸门与网关超时互斥，提交请求必然出现"前端失败、后端成功"

**现象**：§6.4（247–258 行）把"安全扫描完成且未命中红线"列为"提交时同步返回、必须全部通过才允许建版本"的校验项；§15（730 行）要求"单包扫描 P95 ≤ 15s、硬超时 120s、排队超 30s 返回 503"；而 `../../../web/nginx.conf.template` 的 `/api/` location 没有设置 `proxy_read_timeout`，走 nginx 默认 **60s**。
**为什么是问题**：P95 15s 尚可，但硬超时是 120s + 排队 30s = 最坏 150s，远超 60s 网关超时。zip 来源还要先解包 50 MiB。用户会看到 504/连接中断，而服务端可能已经完成扫描并继续代发，产生"用户重试 → 409 已存在"的二次困惑。这不是性能优化问题，是接口形态问题：写操作 + 外部进程 + 分钟级耗时不应当放在同一个请求里。
**影响**：§16.23（786 行）要求"提交返回 422"这一条在真实部署下无法稳定观测；所有涉及"提交"的验收都要改；前端提交页要处理"未知结果"状态（用户不知道该不该重试）。
**建议**：把提交拆成"同步极小校验 + 异步状态机"，PRD 只需改三处措辞：§6.4 标题改为"同步校验清单（不含扫描）"；§6.5 明确"扫描/代发/落库异步，前端轮询 `GET /submissions/{id}`"；§10.3 的 202 响应改为 `{submissionId, status, pollAfterMs}`，red/超时等结果改由轮询返回。同步部分只保留 package.json 解析、SemVer、包名/版本唯一性、压缩包安全（毫秒级）。
**归属**：产品规则

### R3 安装文档只有一条路径，但产品要求"每个版本各有一份文档"

**现象**：§5.2（181 行）提示词固定为 `{publicBaseUrl}/dsh/install/{namespace}/{slug}.md`，并明确"不在提示词中塞版本号"；§5.1（173 行）版本列表"该版本单独的复制提示词"；§5.2（186 行）"版本列表每一行也提供单版本复制（同一句式，**文档指向该版本**）"；§5.3（194 行）文档第 2 段必须写"精确版本"。
**为什么是问题**：URL 里没有版本段，同一插件的 N 个版本只能对应同一个 `.md`，而该文件只能写一个"精确版本"。"文档指向该版本"在路由层面不成立。更麻烦的是多版本并存时：DSH 从索引看到 3 个版本，用户点"复制 v0.2.0 的提示词"，Agent 读到的文档可能写 v0.3.0，装错版本且没有报错。
**影响**：这是路由契约问题，越晚改越贵——索引里的 `versions[]`、详情页复制按钮、安装文档生成器、缓存策略、验收 §16.6/§16.7（754–755 行）全部要跟着改；上线后发现会让 Agent 装错版本，属于"看起来装成功了"的隐性事故。
**建议**：二选一并写进 §5.2/§5.3：① 路径加版本段 `/dsh/install/{ns}/{slug}/{version}.md`，旧路径保留为"指向最新 LISTED 版本"的别名（推荐，兼容 Agent 已记住的句式）；② 保留单路径，但删除"每行单版本复制"，版本选择只影响页面展示，提示词永远指向最新 LISTED 版本，并在文案里写明"提示词始终安装最新版本"。
**归属**：产品规则

### R4 权限矩阵里的五个动作没有接口；"下架 + 重新提交"的迁移路径在唯一性规则下走不通

**现象**：§11（657–663 行）列出"下架、恢复、改分类、重新扫描、黑名单、删除（668 行软删）"；§3.4（113 行）要求空间 ADMIN 能"下架 / 恢复上架"；§9.2 定义 `YANKED` 版本状态、§9.1 定义 `REMOVED` 插件状态。但 §10.2（589–598 行）只有 `PATCH`（改分类）、`rescan`、`waiver`，**没有 hide / restore / delete / yank / blacklist 任何端点**；§16.34（800 行）的验收直接依赖"下架/恢复"。另：§3.4（119 行）给出迁移方案"走下架 + 重新提交"，而 §9.1 `package_name 全站唯一` + §6.4.4 第 4 条（254 行）"私服中 name@version 已存在则拒绝"——下架后旧插件仍占用该 `package_name`，重新提交必然 409。
**为什么是问题**：`YANKED`/`REMOVED` 是**死状态**：没有任何动作能把版本/插件推进去。工程实现时只能靠"猜"，猜出来的 API 与验收文档对不上。迁移路径的直接后果是：想换命名空间或换包名的用户被永久锁死，运营唯一手段是直接改库。
**影响**：§16.34 无法通过；上线后第一批"想把包从个人空间迁到团队空间"的用户就会撞墙；黑名单这个最强治理动作没有入口，等于不存在。
**建议**：在 §10.2 补齐 4 个端点并写明权限与副作用：`POST /plugins/{ns}/{slug}/hide`、`POST .../restore`、`POST .../versions/{v}/yank`、`POST /plugins/{ns}/{slug}/blacklist`（SUPER_ADMIN）。同时把 §3.4 的迁移方案改写为可执行的一条：**下架不释放 `package_name`；换归属需 `REMOVED`（保留审计与 tarball）后由 `SUPER_ADMIN` 释放包名**，并在 PRD 写清"释放后旧 URL 返回 404、旧索引版本立即消失"。
**归属**：产品规则

### R5 审核与代发的先后顺序未定义，两条路径都有产品后果

**现象**：§6.5（262–269 行）流程图顺序是"落库 plugin_version(PENDING/APPROVED) → [需审核] 进审核队列 → 审核通过 → 代发 npm 成功后才可 LISTED"；同一节 272 行却写"代发 npm 失败：整个提交回滚（不落版本）"。
**为什么是问题**：两句话不能同时成立。若先审核后代发：审核人批准的是一个**尚不存在于私服**的版本，代发随后失败 → 已批准的版本没有可安装产物，索引若按"LISTED"收录会产生 404 包（D 组 §16.8 会失败）。若先代发后审核：私服里出现了未经审核的包，任何人只要知道包名就能 `dsh plugin add` 装上，"审核通过才上架"的治理承诺被绕过。
**影响**：状态机与索引收录条件都要跟着定；返工涉及 `plugin_version` 状态集合、审核队列的展示字段（审核人是否需要看到"已代发/未代发"）、以及"代发失败后如何回到待审"的补偿逻辑。
**建议**：明确"**先代发、后审核、通过才 LISTED**"，理由是"被扫字节=被发字节"（§7.4）已经保证了代发产物的可信度，审核是对"是否该出现在目录里"的判断，不是对产物存在性的判断；相应补一条：代发成功的版本在审核期处于 `PENDING`，私服可达但**不进索引**、详情页对非空间成员 404，并在 §11 治理表补一行"审核期包在私服可见"的已知边界说明。
**归属**：产品规则

## P1（明显缺陷，可带病上线但会持续消耗运营）

### R6 "遵循该空间的发布策略"未定义，直接决定要不要新建一套配置

**现象**：§6.1（211 行）"需为所选命名空间的成员（角色不低于 MEMBER），并遵循该空间的发布策略"；§6.5 只区分"需审核空间 / 免审空间"。技能侧既有的免审机制是按成员授予的（`namespace_member.team_auto_publication_grant_id`，`V125__trusted_namespace_publish.sql`），不是"空间开关"。
**为什么是问题**："发布策略"可以指技能那套"成员级免审授权"，也可以指"空间级开关"，两者实现成本与治理含义完全不同：前者意味着某成员对技能免审即对插件也免审（插件权力远大于技能，可能需要单独授权），后者要新增一套配置与 UI（PRD 无此设计）。
**影响**：如果实现成"复用技能授权"，会出现"某人因为技能写得好被授予免审，于是可以不经审核把任意代码推上私服"的越权；如果实现成"新配置"，PRD 缺少这个配置的入口、默认值与审计要求。
**建议**：在 §6.1 加一句裁决："插件的发布策略**不复用**技能侧的成员级免审授权，v1 一律需审核（PERSONAL 空间同样需审核或由 `SUPER_ADMIN` 放行）；v2 再引入空间级插件免审开关"。这是最省实现、也最符合"代发任意代码"风险等级的默认值。
**归属**：需用户裁决（PRD 未定，且影响是否新建配置）

### R7 私有空间插件没有产品定位：审核通过即 LISTED，但市场永远看不到

**现象**：§8.4（479 行）收录条件"所属命名空间为公开空间"；§11（667 行）"私有空间插件不进公开索引，但仍在站内可见（仅空间成员）"；§3.4（117 行）插件 tab 对所有成员可见含 PERSONAL 空间；§3.2 详情页匿名可访问。
**为什么是问题**：私有空间的插件走完审核 → `LISTED` → 但索引排除 → 市场列表与详情页对非成员 404。作者在"我的插件"看到"已上架"，却没有任何地方能解释"为什么同事在 DSH 里搜不到"。同时"复制提示词"这个核心价值对私有空间也失效（提示词指向的文档对非成员 404，同空间成员可以打开但索引里没有这个包，DSH 里根本看不到）。
**影响**：这是**唯一入口即失效**的场景——个人空间（PERSONAL）是默认空间，大量首提交会落在这里，用户第一次体验就是"提交成功但没人看得到"。
**建议**：PRD 明确两件事：① 私有空间插件的状态文案不用"已上架"，改用"已通过（仅空间内可见）"，并在详情页/列表给出稳定说明"该插件所属空间为私有，不会出现在公共索引中"；② 私有空间内的分发路径写清（成员用包名 + 私服地址手工安装，站内提供这条命令），否则 §11 那句"仍在站内可见"没有落地价值。
**归属**：产品规则

### R8 "复制提示词次数"的口径自相矛盾，且在内网 NAT 下会被系统性压成 1

**现象**：§12（674 行）`view` 是"1 次/会话/插件"；§10.1（584 行）去重键是"`pluginId+event+IP hash+日`"；§16.20（780 行）"同一 IP 同日重复上报只计 1 次"。§4.2（152–153 行）卡片展示该计数，但卡片上"不放复制提示词按钮"（153 行），只有详情页能复制。
**为什么是问题**：会话级与 IP+日级是两个不同口径，按后者实现，内网里整个办公区共享出口 IP，**全公司一天只算 1 次**；这个数字还是对外展示的唯一指标（§12 675 行）。另外"卡片展示复制次数、但复制动作只发生在详情页"，意味着这个数字永远只统计"点进来的人"，用来衡量市场页吸引力是错的。
**影响**：上线后这个指标会低到不可解释，运营无法据此判断插件的真实使用意愿；而它恰好是唯一面向用户的数字，错得越久越难纠正。
**建议**：改成"展示曝光次数（`view`，按 IP+日 去重，接受 1 天 1 次的保守口径）+ 隐藏复制次数"，或者把卡片上的数字换成不依赖去重的"已上架版本数/最近更新时间"。若坚持展示复制次数，至少要同步在 §12 写清"该数字为下限估计，NAT 环境下会偏低"，避免运营误读。
**归属**：产品规则

### R9 目录可能收录根本不是 DSH 插件的包

**现象**：§2（42 行）定义"DSH 插件 = 声明 `dsh.bundle` 的 npm 包"；§6.4 第 2 条（252 行）"存在 `dsh.bundle` 或 `dsh` 相关声明（缺失给出警告而非拒绝，兼容早期插件）"。
**为什么是问题**：定义与校验冲突。任何普通 npm 包（只要有 `package.json`）都能过校验进目录，用户在 DSH 里装上之后什么都不会发生，且`dsh plugin add` 是否接受这种包也不确定。
**影响**：目录信噪比下降，且这是**用户装完才发现**的失望，比提交被拒的伤害大得多；同时会让"能力披露"区块显得荒谬（一个纯工具库没有任何 capability）。
**建议**：把规则改成"缺 `dsh` 声明时，插件以 `UNLISTED`（仅站内可见、不进索引）状态收录并提示作者补声明"，或直接拒绝并给明确文案 `plugin.error.notADshPlugin`。二选一都比"警告但收录"好。
**归属**：产品规则

### R10 "私服已存在 name@version"与已删除的"仅收录"概念冲突

**现象**：§6.4 第 4 条（254 行）"私服中 `name@version` 已存在则拒绝"；§12（674 行）仍保留 `download` 事件并注明"仅 `仅收录` 类插件存在"；§11（652 行）仍写"匿名可下载 tarball"。而 §2 名词表、§6.2 来源收敛规则里**没有"仅收录"这类插件**。
**为什么是问题**：内网里最常见的真实情况就是"包已经在私服里了（CI 自己发过），只想把它登记到市场"。当前规则会把这种可用场景判成 409，同时"仅收录"这个能解决它的概念在需求里被删了，只剩两处残留引用（`download` 事件、匿名下载权限）。
**影响**：团队会被迫用"改版本号再发一次"这种脏办法绕过；`download` 事件与匿名下载权限是**幽灵需求**——没有接口、没有 `仅收录` 字段，统计与权限表却为它留了位置，实现时会被当成待办。
**建议**：二选一并清理残留：① 恢复"仅收录"作为一种提交结果（`source=npm` + `tarball_key` 为空 + 不进代发流程），删除 `download` 与匿名下载权限；② 明确"不接受已存在的 `name@version`"，同时把 §12 的 `download` 事件、§11 的"下载 tarball"权限一并删掉。推荐 ②（与 P1 阶段的简化一致），但必须删干净，不能留半句。
**归属**：需用户裁决（是"是否支持登记已有包"的产品决策）

### R11 安装文档没有"如何访问私服"的段落，私服非匿名时安装必失败

**现象**：§5.3（191–198 行）安装文档固定 6 段：标题、需要安装的内容（含 registry 地址）、安装步骤、校验、卸载、安全提示。没有"配置 registry / 凭据"的步骤。而 R7（815 行）"私服实现未定"，§4.1（142 行）只提示索引源要用 `https`。
**为什么是问题**：`dsh plugin add` 最终要访问 npm registry 拉包。如果私服需要认证（企业私服默认要），用户按文档执行必然 401，而文档没有任何补救段落，本站也无法感知这次失败（无回传）。这个失败发生在"用户已经完成任务、只差一步"的时刻，是最伤的一步。
**影响**：§16.7（755 行）"文档含…且不含任何 Token"能过，但真实安装成功率无法保证；上线后客服会收到"按文档装了但报错"的一类工单，而 PRD 没有任何可执行的答复。
**建议**：在 §5.3 增加第 7 段"如果安装报权限错误"，写清两条路径（配置 `.npmrc` 的 `//registry/:_authToken` 或联系管理员开通读取权限），并且**前提是先裁决"私服是否强制匿名只读"**：如果是，本段写成"本站私服已开放匿名只读，无需配置"；如果不是，本段必须给出凭据获取流程。
**归属**：需用户裁决（私服匿名读是硬前置，决定本段内容）

### R12 验收条目有 7 条不可客观判定，且 P1 出口条件引用了它们

**现象**：§16.1（746 行）"「发现」页能看到该插件卡片"、§16.3（748 行）"DSH 能解析到图标并正常显示"——依赖真机 DSH；§16.19（776 行）"403 **或**空命名空间列表"、§16.35（801 行）"403 / 空态"——两种结果都算通过；§18（836–837 行）出口条件直接写"验收 A/B/C(部分)/D/H(31–33) 通过"。另外 §15（729 行）"索引走 CDN/对象存储缓存"在内网私有化部署下没有 CDN 可交付。
**为什么是问题**：出口条件引用了不可判定的条目，等于出口条件不可判定。"403 或空列表"两种行为对安全含义完全不同（空列表会让人以为空间没插件，403 才明确拒绝），二者不能都算通过。CDN 要求在本部署形态下无法满足，属于写了但没有交付物。
**影响**：验收会变成"评审会上争论"，而不是"跑一遍就知道"；灰度与发版决策缺少客观依据。
**建议**：给每条验收加固定标签 `[自动]` / `[真机]` / `[人工]`：真机条目（1、3、29）抽成一份固定手工脚本（DSH 版本、profile、步骤、期望截图位），并把"装成功"作为唯一真机门禁；把两处"或"统一成 403（与 §10.2 的 403 一致，且不泄漏存在性）；§15 的 CDN 改为"对象存储 + 短缓存（`max-age=60`）+ `ETag`/304"。
**归属**：产品规则

### R13 审计清单漏掉了四类高风险动作

**现象**：§11（665–666 行）要求审计的是"提交、上架、下架、删除、审核决定"+"扫描相关（放行/撤销、重扫、漂移自动下架）"。未覆盖：**代发 npm（写入私服）**、**改分类**、**黑名单**、**恢复上架**。
**为什么是问题**：代发是"把代码推进所有人可安装的通道"，是整条链路上风险最高的写动作，却是唯一没有审计要求的；改分类会改变索引里的结构（影响检索与分类浏览）；黑名单是"全站禁止"这一最强动作；恢复上架是"撤销一次治理决定"。四者都符合 AGENTS 对"发布/删除/授权链路必须留痕"的要求，属于漏项而非有意豁免。
**影响**：事故复盘时无法回答"这个包是谁、什么时候、用哪个 tarball 推进私服的"；`sha512` 与 `fingerprint` 都在库里但没有与操作人关联。
**建议**：§11 审计清单补四项，并规定 `detailJson` 必含字段：代发（包名、版本、`sha512`、registry、结果码）、改分类（旧值→新值）、黑名单（理由、影响范围）、恢复上架（理由、当时最新裁决）。
**归属**：产品规则

### R14 `latest_version_id` / "更新时间"语义未定义，但它们是索引排序键

**现象**：§9.1（513–514 行）`latest_version_id` 与 `latest_scan_verdict` 标注为"冗余指针，便于列表""随 latest_version_id 一起维护"；§5.1（167 行）详情页展示"更新时间"；§8.2（456 行）`versions[].publishTimestamp` 是索引排序依据（§4.2 157 行"默认排序 = 发布时间倒序"）。
**为什么是问题**："latest"可以指最新提交、最新 LISTED、最新 APPROVED 三种；`YANKED` 之后回退到哪个版本没有定义。详情页"更新时间"可以是版本发布时间、元数据修改时间、最近扫描时间——三者会让同一个插件在不同页面显示不同"新"。一旦索引排序键取错，市场默认排序就不可解释。
**影响**：卡片排序与详情页默认选中版本会在"撤版/拒审"场景下出现不一致；这类 bug 极难被验收发现（§16 没有任何一条覆盖"撤版后列表顺序"）。
**建议**：在 §9.1 写明三条定义：`latest_version_id` = 最新 `LISTED` 版本（无则最新 `APPROVED`）；`publish_timestamp` = 版本首次进入 `LISTED` 的时间，**撤版后重新上架不刷新**；详情页"更新时间" = 最近一次元数据变更（分类/简介/图标），与索引排序解耦。并在 §16 补一条"撤版后列表排序不变、默认版本回退正确"的验收。
**归属**：产品规则

### R15 索引"事件驱动重建 + 60s 缓存"叠加，产品没写生效时延

**现象**：§8.5（486 行）"触发：任一插件/版本状态变化后重建（事件驱动），非定时扫描"；§8.1（432 行）要求 `Cache-Control: public, max-age=60`。
**为什么是问题**：两者叠加，用户改完分类或完成审核，最长要等"重建完成 + 60s 缓存过期"才在 DSH 里看到。PRD 全文没有任何地方告诉用户"多久生效"。更严重的是"每个事件触发一次重建"在批量场景（§7.7 升级全量重扫 → 数十个插件同时变 red）会连续触发几十次全量重建，成本与抖动都不合理。
**影响**：作者会反复刷新、反复改、以为没生效；运营批量下架时会看到索引反复重建。这类问题会以"体验不好"的形式反馈，但根因是需求没写延迟预算。
**建议**：在 §8.5 加两句：① "重建为合并式调度：状态变化只标脏，由后台任务合并重建（连续变化合并为一次），端到端生效目标 ≤ 2 分钟"；② 在「我的插件」与详情页写明"索引最长 1 分钟生效"的文案。产品侧只需接受这个时延并写进文案，不需要新功能。
**归属**：技术补强（+文案）

### R16 没有工具回答"这个插件为什么没进索引"

**现象**：§8.4（476–482 行）给了 5 条收录条件；§3.4（110 行）空间插件列表列的是"状态、分类、裁决"，没有"是否已收录"；§10.2 没有管理员视角的提交记录查询（只有 `GET /dashboard/plugins` = 我提交的）。
**为什么是问题**：5 条条件中任意一条不满足，用户看到的现象都是"市场里搜不到"，而站内没有任何地方能显示是哪一条。运营与客服只能靠查库。这是上线后最常见的工单类型（"我明明上架了"）。
**影响**：每来一次工单就要一次人工查库，且判断依赖对 5 条规则的口头记忆；接入方（团队）无法自查。
**建议**：在「我的插件」与空间插件列表各加一列"索引状态"（已收录 / 待重建 / 未收录：空间为私有 / 未收录：最新版本裁决为红 / 未收录：无已上架版本），取值直接来自索引生成时的同一段判定逻辑（复用而不是重写）；不需要新页面。
**归属**：产品规则

### R17 升级漂移会产生批量下架，但没有处置界面

**现象**：§7.6（403 行）"升级触发的重扫：后台任务批量重扫…若结论由 clear 变 red，自动下架（HIDDEN）并告警"；§3.4（119 行）明确"不做空间级别的批量操作"。
**为什么是问题**：一次扫描器升级可能同时让十几个插件下架，运营需要逐个确认"是误报还是真问题"、逐个决定"放行还是保持下架"。批量动作本身可以不做，但**批量结果的可视化与批量跳转**必须有，否则运营只能在告警邮件里手工对名单。
**影响**：升级当天的工作量从"看一张清单"变成"在列表里逐个搜索"；漏处理一个就会长期挂着"该插件已下架"的困惑。
**建议**：不新增批量操作，只要求"漂移重扫任务产出一份差异清单"（版本、旧裁决、新裁决、命中 code、操作链接），告警里附清单链接。列表页支持 `?scanDrift=1` 筛选即可。
**归属**：产品规则

## P2（打磨）

### R18 导航把"实验性"能力排在成熟能力之前

**现象**：§3.1（66–71 行）导航顺序改为 首页 / **插件市场** / 技能市场 / 技能套件 / 控制台，插件市场占据原「发布」的第 2 位；而 §4.1（139 行）自己说明 DSH 侧入口是"插件 → **实验性插件** → 自定义插件索引"。
**为什么是问题**：把一个需要用户先在 DSH 里打开实验开关才能用上的能力，放在站内第二导航位、排在成熟技能市场之前，会给用户"这是主推功能"的预期；插件侧 v1 没有任何存量内容（首屏必然是空态）。
**影响**：首屏空态 + 高曝光 = 第一印象是"这个市场没东西"。这是可测的（导航顺序），但改起来涉及布局与埋点。
**建议**：插件市场放在"技能市场"之后（首页 / 技能市场 / 插件市场 / 技能套件 / 控制台），并在空态里放"成为第一个收录的插件"入口承接流量。
**归属**：产品规则

### R19 图标规则三处不一致，会直接产出 404 图标

**现象**：§8.2（449 行）索引 `plugins[].icon` 固定为 `icons/{pluginKey}.svg`；§6.4 第 7 条（257 行）允许图标是 SVG/PNG/JPEG/WebP 且"≤ 32 KiB（内联时）"；§6.3（241 行）图标来源是"包内 `icon`/README 首图，切图后转 data URL 或存图标文件"。
**为什么是问题**：三个决定互斥——索引只能写 `.svg` 路径，但允许 PNG/WebP 上传；"data URL"与"存图标文件"是两种存储；"README 首图"需要拉取与渲染。若按最省实现（只取包内 `icon`、按实际类型存 `icons/{key}.png`），索引里的 `.svg` 就是错的；若按索引写死 `.svg`，PNG 图标会 404 或内容类型不符。
**影响**：图标是卡片的第一视觉，404 会让整排卡片退化成占位符，属于"一眼可见"的质量问题。
**建议**：在 §8.2 把字段改为 `icons/{pluginKey}.{ext}`（ext 取实际字节类型），并明确"不抓 README 首图（避免出网与渲染链）"、删除"data URL"选项（统一走对象存储）。
**归属**：产品规则

### R20 文档内部数字与承诺不自洽，会让实现漏项

**现象**：§3.1（74 行）"`/dashboard/publish` 路由与**其 5 个查询参数**（`namespace`/`visibility`/`updateName`/`updateSkill`/`resubmitSkill`/`resubmitVersion`）"——实际列了 6 个；§13（686 行）"新增 **4 条**路由（§3.2）"而 §3.2（82–86 行）列了 5 条且 §13 后面又单独补了第 5 条；§9.4（567 行）说"聚合到计数表"，但 §9 没有给出计数表；§6.2/§6.3 把 folder 与 zip 写成两条来源，而 §6.2（223 行）自己说文件夹"走 zip 同一链路"。
**为什么是问题**：这类数字错误会直接变成实现漏项——"4 条路由"会让工程师少建一条（最可能漏的是命名空间插件页，而它恰好是 H 组验收 33–35 的对象）；"计数表"缺失会让统计实现临时发明结构，与后续 PRD 修订对不上。
**影响**：返工小但确定发生；且这类不一致会在评审时反复消耗讨论时间。
**建议**：一处一处改数字（5→6、4→5），§9.4 补一张 `plugin_stat_daily(plugin_id, date, event, count)` 的字段级定义，§6.3 把"文件夹"标注为"zip 的 UI 变体，不是独立链路"（与 R5 的兼容性风险一致）。
**归属**：产品规则
