## 2. 完整修订说明

> **修订说明（历史记录，现行正文以各节为准）**: 下方各版说明为演进而非现状；凡出现"先代发后审核"的表述、「撤包」、「已代发（审核中）」等措辞均为**已被 v2.8 反转的旧口径**，仅用于追溯，不得据此实现。

> **分段说明**：每节标题里的短语，就是原文那句加粗小标题——只是把它提升成了标题行，正文其余文字**一字未改**。原文按版本号顺序排列，v2.11 与 v2.2 是被后续版本推翻的旧口径，保留仅作追溯。

### v2.0

已剥离技术设计（数据结构、接口、错误码、渲染实现、组件/路由/数据层清单、后端分层、部署配置、i18n 键、超时并发缓存数值一律移出 → `openspec/changes/add-plugin-market/design.md`，章节对照见 `plugin-market-v1.0-prd-tech-handover.md`）。

### v2.1

按研发评审 R1–R20 修订。

### v2.2 — 按用户裁决改两条

① 提交链路改为「扫描 → **代发** → 审核 → 上架」（用户采纳研发原方案），并补齐两条产品规则——**审核拒绝即撤包**（撤不掉则撤版 + 永不进索引 + 详情 404）与**审核期已知边界**（包已在内部源可被安装，审核页/详情页显式标注"已代发（审核中）"+ 内容指纹）；② **取消 7 天时效自动重扫**，审核使用提交时的报告，风险在 §13 R8 显式接受。其余不变：市场卡片不展示计数（§10）、导航技能市场在前（§3.1）、真机判据三条可判定（§11 末）。

### v2.3 — 冻结前补三条裁决（只加内容、章节号不变）

①「待发布」态对非成员按未上架处理、空间成员可见失败原因与重试入口（§8.4，§6.6 引用）；②黑名单对存量版本即刻下架、下一轮索引重建剔除、安装文档与全部路径 404，包文件保留取证但永不再进索引（§9、§8.4）；③撤销放行导致自动下架必须站内通知作者与该次放行的审核人，沿用现有站内通知渠道（§7.4）。

### v2.4 — 与架构师对齐 design 定案后补三条微补丁（仍不加小节、不动编号）

①撤掉最后一个可上架版本时插件自动转为未上架，作者看到"已无可安装版本"，不允许"已上架但无可安装版本"（§8.5）；②包名冲突改三分支——黑名单 / 已下架未释放 / 已被他空间收录，三种都当场拒绝但下一步不同（§8.5）；③「浏览」只落库、v1 不提供任何界面展示、不向作者开放，v1 唯一对外计数仍是详情页「复制提示词次数」（§10）。

### v2.5 — 补交付边界（仍不动章节号）

提交仅对个人空间开放，团队空间提交入口**置灰**并说明"审核与撤包将在治理阶段同批开放"（不隐藏）；P1 在「审核接入 + 撤包同批就绪」后开放团队空间提交，且**验收第 16 项（拒绝→撤包/撤版降级路径）列为 P1 出口条件**，不是可选项（§12 P0/P1 两行，未新增验收条目、未改表格结构；**此句随 v2.8 链路反转作废，见下方 v2.8**）。

### v2.6 — （真最后一条，此后冻结）

§6.1 新增**入口可用性通用规则**——提交入口可用性由"该空间当前是否开放提交能力"决定，不可用时**置灰并说明原因、不隐藏**（入口消失会让用户以为功能没了）；写成通用规则而非 P0 专属，避免 P1 开放团队空间时再改一次，也让今后任何"某类空间暂不支持"有统一处置。

### v2.7 — （冻结稿最后一次修改）

§12 P0 出口条件由"C 中 8、10、11、12"改为"C 中 8、10、12 与 11 之③（①② 依赖黑名单与软删，随 P1 治理能力验收）"——第 11 项扩为包名冲突三分支后，①② 依赖 P1 治理能力，P0 无入口可测，出口条件必须可判定；③"已被他空间收录"在 P0 提交校验即可验，故留在 P0。

### v2.8 — 按用户裁决推翻 v2.2 的链路，改回「扫描 → 审核（如需）→ 代发 → 上架」

（一次净删减）：① 团队空间**先审核、通过后才代发**，代发成功才上架；个人空间免审，扫描通过即代发、成功即上架；② **审核拒绝 = 不发布**——不代发、不产生任何制品、不进索引，作者看到理由可重提，"拒绝即撤包 / 撤不掉则撤版 + 404 / 已拒绝（残留于内部源）"整段删除（拒绝时代发尚未发生，没有包要撤）；③ **删「审核期已知边界」**及详情页/审核页「已代发（审核中）」标识要求，审核页改为展示"该版本尚未发布，通过后才会推送到内部源"+ 内容指纹；④ **新增用户可见态「已通过审核，等待发布」**——审核通过后代发失败时作者可见、可见脱敏原因、可重试，**审核结论不因代发失败回滚**；⑤ 验收第 16 项重写，§13 风险表删"审核期包可被安装"与"撤包依赖私服能力"，新增"审核通过后代发长期失败"；⑥ Git 来源表单口径：接受 `https://` 与 `git@host:path`，提交前预检分类提示，**凭据由平台配置、用户不填任何 token/密钥**。

### v2.9 — 定 Git 来源最终口径

用户**只填仓库地址**，不填凭据、版本、分支或 tag；一律取**默认分支的最新提交**（§6.2 表、§6.3 表单、§6.4 第 6 条）；新增"同一仓库重复提交但版本号未升级 → 提示'该版本已存在，请先在仓库中升级版本号再提交'"（§6.4 第 4 条、§6.6）与风险 R10「默认分支随时可能被推进」（§13）。

### v2.10 — 修 v2.8 的连带漏改（只改验收项，不动章节号）

验收第 8 项进度顺序由"发布到内部源 → 等待审核"改为"**等待审核 → 发布到内部源**"（该项是 `[人工]` 走查项，顺序反了 QA 会照错念）；验收第 9 项"commit 与仓库实际一致"改为"**提交号与仓库默认分支最新提交一致**"（与 §5.1 展示口径一致）。

### v2.11 — Git 子目录定稿（初版口径，v2.12 起作废，不得据此实现）

表单曾增加**选填**「子目录（插件所在目录）」（默认根目录；分支/tag/commit 仍不填），不填时按 §6.4 第 6 条自动探测（**恰好 1 个含 DSH 插件声明的包才采用**，0 个报错、多个列候选不猜）；§5.1 曾展示**服务端解析出的最终子目录**；曾新增风险 R11（默认分支推进后仓库结构变化，已上架版本固定在提交那一刻的解析结果）。**以上子目录口径已被 v2.12 全部推翻，仅留追溯。**凭据实现与传输层细节一律不进产品文档，全文只写"凭据由平台配置、用户不填"。

### v2.12 — 按用户裁决推翻 v2.11 子目录口径（净删减，章节号与验收编号不变）

Git 来源**只有一个输入框：仓库地址**，**禁止子目录输入框**，禁止填分支 / tag / commit / 任何凭据；**一个插件一个仓库**，插件包必须位于**仓库根目录**——用户不提供任何"包在哪里"的信息，位置由规范决定、不是用户选项；取该仓库**默认分支的最新提交**（沿用 v2.9 口径，不回退）。删除自动探测三步与"多个候选列路径让用户填子目录"整段；§6.4 第 6 条改为校验**仓库根目录存在含 DSH 插件声明的 `package.json`**，不符合按固定文案报错、**不提供任何让用户填路径绕过的入口**；预检四类提示（不可达 / 无权限 / 仓库不存在 / 不在允许范围）不变；§5.1 只展示仓库地址 + 提交号；§13 删除 R11，风险表现恢复 R1–R10；已上架版本固定在提交那一刻的规则保留。逐条处置见 `plugin-market-v1.0-product-review-response.md`。

### v2.13 — 按用户裁决收窄 npm 包名来源（净删减，章节号与验收编号不变）

npm 来源**用户只填包名（可 scoped），禁止手动输入版本**，表单不得出现版本输入框，分支 / tag / commit / 凭据同样不填；版本由服务端取 registry `latest` 对应的**最新非预发布版本**（跳过 prerelease），**在提交那一刻冻结**并写入该次提交快照，扫描 / 审核 / 代发 / 上架全程复用，后续阶段不得重新解析 latest；上游 npm 发新版本**不影响已上架版本**，要上新版必须重新提交；重复提交且 latest 未变、该 `name@version` 已存在 → 409 拒绝，固定文案"该版本已存在，请先在上游 npm 发布新版本后重新提交"（不沿用 Git 的"先在仓库中升级版本号"）；**任何途径传入版本都不受理**（产品红线）。逐处改 §6.2 / §6.3 / §6.4 / §6.6 / §11 第 11、16 项 / §13（新增 R11，风险表现 R1–R11），§12 核对无 npm 版本表述、未改。v2.11 子目录口径与 v2.12 旧 R11 仍为历史作废记录，不得据此实现；本次新增的 R11 是 npm 专属，与旧 R11 无关。

### v2.14 — 按用户裁决补一个真实产品缺口

（用户原话："审批页面缺少查看插件的文件内容详情，审批人在审批时，无法人工审核插件代码是否存在问题"）：审核页新增**包内文件浏览**——审核人可看本次提交暂存包的**文件清单（目录树 + 每文件大小）与单文件文本内容**，用于人工审查代码；展示内容**必须与审核页的 sha512 内容指纹是同一份字节**（不得改从内部源 / 上游 npm / Git 仓库拉取，否则"审的"与"发的"不是同一份东西）；**只读纯文本是红线**——任何包内文件都不得在站内被当作可执行内容渲染（不渲染包内 HTML / SVG、不执行包内 JS、不加载包内资源）；二进制只显示类型与大小，单文件 > **512 KiB** 不内联、改「下载查看」；`.env` / `*.pem` / `*.key` / `id_rsa` 一类敏感文件名只做**视觉标记、不阻止查看**；仅空间审核人与作者本人（自己的提交）可见，非成员 403；**查看 / 下载均写审计**；**不改变审核依据仍是扫描报告 + 人工判断**，对外仍只有四种裁决表述。逐处改 §6.5（新增「审核页的包内文件浏览」块，含暂存包保留期）、§7.3（审核页加一句引用）、§9（审计事件加一条）、§11 第 16 项（补人工走查要求，验证方式改 `[自动 + 人工]`）、§12 P1 行（范围写明含包内文件浏览）、§13（新增 R12）；**章节号未变、未新增小节、验收仍 27 条**。

### v2.15 — 按用户裁决再收敛四处（章节号与验收编号均未变，验收仍 27 条）

① **详情页不再允许用户选版本**——安装永远取当前最新已上架版本，页面只留一个只读版本号与一个「复制提示词」，版本列表降为只读历史；提示词与安装文档**仍带版本段**，版本由服务端在复制那一刻渲染（§5.1、§5.2）。② **审核页包内文件清单必须按目录层级展开、目录节点可折叠**，禁止把全部文件平铺成一列完整路径（§6.5 第 1 条）。③ **全文收敛"代发"口径为"发布 / 上架"**：只有 zip / 文件夹来源需要平台代用户发布成 npm 包进内部源，npm 与 Git 来源本就有可分发位置、不需要代发，这是内部实现差异、**不得出现在任何用户可见文案里**（审核页、进度、失败原因、风险提示一律只见"发布 / 上架"）；§6.5 链路改为「扫描 → 审核（如需）→ 发布 → 上架」，阶段名改为"上架中"（触及 §6.1、§6.2、§6.5、§6.6、§7.2、§7.4、§8.1、§8.4、§9、§11、§12、§13）。④ **索引里的分发来源与上传方式无关**——生成期逐个已上架版本判定：内部 npm 镜像里已有该包的该版本就写 npm，缺失才退回该版本的 Git 仓库地址 + 提交号，两者都无则该版本不得上架（§8.2、§8.6，新增 R13）。

### v2.16 — 按用户裁决补一个真实产品缺口：插件可见范围
