| 21 | **PRD 未涉及（治理规则）**：`PRD §9` 矩阵「审核插件版本（团队空间）」只写"空间管理员 ✓"，既没排除、也没允许"提交者本人恰好是该空间空间管理员"的情形 | **允许自审**（用户裁决）：`submitted_by == actor` 时 approve / reject 都正常执行，不拦截；但审计 `PLUGIN_REVIEW_APPROVED` / `PLUGIN_VERSION_REJECTED` 各带必填字段 `selfReview: true\|false`，审核页在裁决按钮旁显示中性提示「你是本次提交的作者」（由服务端下发 `isAuthor` 决定渲染，前端不推断角色） | 单人空间、或空间只有一个管理员时，**拦掉自审等于审核永远做不了**——功能会在这个最常见的场景里直接失效，所以选择"允许 + 留痕"而不是"禁止"。留痕解决的是另一个问题：不加 `selfReview` 字段，事后无法区分"别人审的"和"提交人自己批的"，复盘与治理报表就失去依据。**代价也要写清**：自审通过时没有第二双眼睛，§14.1 A18 的审核质量风险无法靠流程消除，只能靠"必看项前置 + 中性提示 + 审计可追溯"缓解 | §4.6、§7.2、§7.4、§7.6.6、§10.2、§10.5、§12.1、§16 S15 |
| 22 | `PRD §6.3`（v2.16 引入，**v2.17 定稿**）：可见范围「提交后可改」——**缩窄立即生效**；**放宽在 v1 没有单改入口**（变宽被拒并提示"如需放宽请重新提交"，只能随新版本提交一并发生） | **v1 只实现缩窄**：新增窄端点 `PATCH /api/v1/plugins/{ns}/{slug}/visibility`，只受理 `PUBLIC→NAMESPACE_ONLY`、`PUBLIC→PRIVATE`、`NAMESPACE_ONLY→PRIVATE` 三条路径（立即生效 + 写审计 `PLUGIN_VISIBILITY_CHANGED` + `markDirty`）；任何变宽请求 → **409 `PLUGIN_CONFLICT_VISIBILITY_WIDEN_PENDING`**（`plugin.error.visibilityWidenPending`）+ 固定文案「v1 不支持放宽可见范围，如需放宽请重新提交」 | **已与 `PRD v2.17` 对齐，不算偏离**（保留本行仅作决策追溯）：v2.16 曾要求"放宽需提交审核"，但 `ReviewSubjectType` 只有 `PLUGIN_VERSION`、没有 `PLUGIN_VISIBILITY`，实现它要连带改 `ReviewService` 分流、审核队列查询、审核页字段块与权限矩阵四处——而本变更对既有代码的唯一侵入点已经花在 `PLUGIN_VERSION` 上（§13 #12）。因此 v2.17 把产品口径改成"放宽随新版本提交"（新版本本来就要过 `PLUGIN_VERSION` 审核，团队空间等于仍过审核；个人空间本来免审）。反向风险也写清：**缩窄是安全方向，所以立即生效不需要审核**——延迟缩窄（等审核）恰恰会让"我想马上藏起来"落空 | §7.2、§7.4.1、§10.2、§10.5、§14.2 Q11（已裁）、§15 P1 |


> 未偏离但需要显式记录的**四处接口「PRD 未涉及（接口层，产品无承诺）」**——注意与上表的"PRD 未覆盖"区分：**未覆盖**=产品侧该写没写（如第 18 条的安装文档语义），**未涉及**=PRD 按 v2.0 的剥离规则刻意不写接口路径/端点/能力开关，不属产品漏项、也不需要产品补：`/api/v1/plugins/market`（索引源段需要后端下发索引地址与状态，`PRD §4.1` 只说"由后端生成"；`PRD §4` v2.19 ⑦ 已去掉"模块一"概念）、`POST /submissions/{id}/cancel`（状态机需要作者撤回出口）、`GET /api/v1/plugins/submit-capabilities` + 空间侧 `pluginSubmitEnabled` 字段（`PRD §6.1` 只给了"按空间提交能力置灰不隐藏"的规则，没给能力从哪里来；能力必须服务端下发，否则前端要硬编码分期常量，P1 开放团队空间时得再改一次前端）、`GET /submissions/{id}/files` + `/files/content` + `/files/download`（第 19 条：审核人要确认包内容，但 PRD 只给了"确认"这个能力，没给查看方式）。前三处已在 §7.1/§7.2 定义（`cancel` 列为 P3 可选项，v1 用"重新提交"覆盖即可，见 §15），第三处见 §7.2 与 §10.1，第四处见 §7.2、§7.6 与 §10.2。

## 14. 风险与待确认

### 14.1 `PRD §13` 的补充：异步化与"先审核后代发"带来的新风险

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| A1 | **索引延迟窗口**：状态变化到用户可见之间隔了 1 个 submission 周期 + 1 个索引周期（典型 5–15s，最坏叠加重试更久） | 用户"上架了但 DSH 里没有" | 前端文案明确"索引将在 1 分钟内更新"；`plugin.index.dirty.age` 监控；状态变化后前端轮询 `market` 查询直到 `dirty=false` |
| A2 | **轮询放大** | 大量用户同时提交时，`GET /submissions/{id}` 把 QPS 放大 10–30×（每 2s 一次） | 服务端下发 `pollAfterMs`（退避到 5s）；前端 `refetchIntervalInBackground=false`；该接口限流 120/min/user；终态立即停止 |
| A3 | **worker 与 API 同进程**：worker 在 server 进程内，长事务/慢扫描会占用 API 线程 | API P95 抖动 | worker 走独立 `@Scheduled` + 自己在事务外做网络调用（与既有 outbox dispatcher 一致）；扫描与代发不在数据库事务内；`lease` 覆盖最坏路径 |
| A4 | **多副本下的重复执行**：lease 过期但进程仍活着（GC 停顿/长扫描） | 同一 submission 被两个副本处理 → 重复代发 | 代发前重新确认 `lease_until` 归属（`lease_owner` 校验）；私服 `name@version` 幂等（同内容重复 PUT 幂等）；`plugin_version` 唯一约束兜底；最终以 DB 唯一冲突或私服 2xx 幂等收敛为 `LISTED`（幂等成功）而不是错误 |
| A5 | **`plugin_submission` 表膨胀** | 表与索引持续增长 | 终态行 180 天后**只清大字段不删行**（`source_payload`/`error_detail`/`staged_tarball_key` 置空，见 §6.3）；活动唯一索引是部分索引，不随历史行变大 |
| A6 | **指针缓存各副本不一致（≤60s）** | 同一时刻两台 server 返回不同 `gen` 的索引 | 可接受：DSH 单次拉取取一份；`ETag` 按 `gen` 派生，跨副本切换后客户端会拿到 200 而不是错误的 304（因为 `gen` 变了） |
| A7 | **Git 浅克隆不支持任意 SHA**（`allowReachableSHA1InWant` 多为关闭） | 用户直接填 40 位 commit 时可能拉不下来 | 降级路径：按 ref 浅克隆后**校验**解析出的 commit == 目标 commit，不等即 `gitUnresolved`；不退回全量克隆。**预检也验不了这一点**（`ls-remote` 只列 ref），页面文案写明"预检通过不等于该 commit 一定能拉下来"（§3.4.1） |
| A8 | **Git 仓库炸弹**（超大仓库/子模块/符号链接） | 磁盘与时间耗尽 | 浅克隆 `depth=1` + `singleBranch` + 超时（60s）+ 目标目录大小上限；导出时跳过符号链接与子模块；本期无用户可控 path（包固定在仓库根目录），克隆层禁 symlink 是通用约束 |
| A9 | **`awaiting` 状态在扫描器重启后丢失** | submission 卡在 `SCANNING` | lease 过期即被重新认领，从头再跑（扫描幂等，`tarball` 已在暂存区）；`attempt_count` 上限兜底 |
| A10 | **`dedup_key` 密钥缺失** | 统计去重失效，计数虚高 | 缺失时降级并在 health 报 WARN；不阻断功能（统计不是关键路径） |
| A11 | **审核通过后代发长期失败**（"先审核后代发"的直接代价）：版本停在 `APPROVED`，审核结论已生效但制品上不了架——插件始终不对外可见，作者等不到结果 | 作者体验上是"卡住了"：已经通过审核却什么都没发生；若无人盯，可能无限期挂着 | 三条缓解，缺一不可：①**审核结论不回滚**——重试不重走扫描与审核（重复审同一份产物没有意义），`POST .../publish {action: RETRY}` 由作者与管理员双向可用；②**可见的等待**——「我的插件」在途区显示「已通过审核，等待发布」+ 脱敏原因 + 已重试次数，`plugin.review.approved.age` 是独立指标，>30min 即 P2；③**连续失败告警**——`publish_attempt >= maxAttempts` 或同一 `name` 24h 内失败 ≥3 次即 P1，附 `name@version` 与最后一次错误码。**不做**的：不把 `APPROVED` 当"近似上架"对外可见（索引里没有制品，DSH 装上会 404）；不静默丢弃（静默等于作者永远等不到结果） |
| A12 | **报告可能过时数天**（不做 7 天时效自动重扫） | 审核人基于一份若干天前的扫描结论批准；期间上游包内容若变化（同版本内容被重发、私服被替换），审核结论与实物不符 | 已评估并**接受**，理由：自动重扫会导致"审核时报告刚过期 → 无限重排"，且报告新鲜度靠定时器解决是治标。缓解：①提交时报告的**生成时间 + 工具版本 + 指纹**在审核页常驻展示（§4.6 字段表），让审核人自己判断；②作者重新提交即触发全量重扫；③管理员可对任一版本手动 `.../rescan`；④"扫的就是发的"断言仍在——索引生成期比对 `plugin_version.sha512` 与最新成功报告的 `tarball_sha512`，不等即构建失败并告警 |
| A15 | **默认分支随时可能被推进**（`PRD §13` R10）：同一仓库连续提交、默认分支前进后，包内 `package.json` 版本号可能没改 | 作者以为"再提交一次会更新插件"，实际命中 §6.4 第 4 条"版本已存在"；这是**产品认知差不是系统故障** | ①版本指纹记 `commit + branch + resolved_at`，已上架版本锁定提交那一刻的默认分支，后续仓库再提交不影响它；②唯一性判定是 **`package_name@version`**，commit 未变但版本号改成 1.0.1 **放行**（这是 R10 规定的正确升级路径），commit 变了但版本号没改仍 409，页面固定文案「该版本已存在，请先在仓库中升级版本号再提交」；③详情页"提交号"显示解析出的 commit，让作者判断"这次到底取了哪一版" |
| A14 | **SSH 传输的信任前提**：host key 未 pin、私钥泄漏、容器以 root 运行、密钥轮换期两把钥不一致 | 中间人可以冒充内网 Git（拉回被篡改的源码，扫的与发的都被污染）；私钥泄漏可被用来读其他仓库 | 四道硬前提写进部署文档并做启动断言（§3.4.1）：① `known_hosts` 缺失即启动失败，**不存在"信任任意主机密钥"的开关**；② 私钥只走 secret 文件挂载（0600、非 root 可读），**禁止环境变量传私钥内容**；③ 容器非 root；④ 双钥轮换窗口（主钥失败回退 `_KEY_PATH_NEXT`）。另加一条运维动作：SSH 模式下每季度轮换一次部署密钥，轮换后重跑预检。 |

| A17 | **预览接口本身成为攻击面**（本次新增的能力带来的新面）：① **存储型 XSS**——包内 `.html`/`.svg`/`.js` 若以可渲染类型返回或被前端 `innerHTML` 插入，就等于第三方代码在本站域名下执行（可读 Cookie/发同源请求）；② **路径穿越**——`path` 参数被拼进文件系统/tar 读取，读到包外文件；③ **解压炸弹**——50 MiB 压缩包解出几十 GB、或 100 万个小文件，把 CPU/内存/磁盘打满；④ **敏感信息外泄**——`.env`/`.npmrc`/私钥被**无权限者**（非审核人、非作者）读出 | 1 次 XSS = 全站会话失守；1 次穿越 = 服务器任意文件读；1 次炸弹 = 整个实例被一个提交打挂；1 次越权预览 = 作者误打进包里的凭据泄漏 | 四类各自的缓解都已写死、逐条可测：① 响应类型只允许 `text/plain`/`application/json`，三件套响应头（`nosniff` + `CSP default-src 'none'; sandbox` + `no-store`）+ 前端禁 `innerHTML`/`iframe`（§7.2 硬约束表、§10.2）；② 三层路径防护：物化阶段拒绝 `..`/绝对路径/盘符/NUL/反斜杠/符号链接，请求层白名单**逐字节比对**（接口签名只接受 `StagedFileEntry`，从类型上禁止拼接），读取层再复核（§7.6.1），编码/大小写/并发三种绕过口径各有测试；③ 六项上限（文件数 2000 / 整包 200 MiB / 单文件 8 MiB / 文本 512 KiB / 压缩比 10:1 / 请求预算 5s+10s）+ **超限拒绝整次浏览而非截断**（§7.6.2）；④ 权限**只给该空间空间管理员（`ADMIN`）+ 提交者本人**——平台管理员（`SKILL_ADMIN`/`SUPER_ADMIN`）按 `PRD §9` 矩阵**不在**「审核插件版本」那一行，也不在这里；其他空间成员、他空间成员与非成员一律 403、提交不存在 404（§7.6.6），且三个事件全部写审计、审计失败即不返回内容（§7.6.5）。另加一道**可一键止血**：`SKILLHUB_PLUGIN_FILE_BROWSE_ENABLED=false` 直接关掉整组端点（503），不影响提交与审核决定 |
| A18 | **审核质量风险：审核人只看少数文件就点「通过」**（与 `PRD §13` 的 R12 同类问题；预览能力反而可能放大它——有了"能看"的入口，"没看完"就更容易被当成"看过了"） | 审核变成形式化签核：真正的问题代码在一个 2000 文件包的第 1800 个文件里，没人会翻到；更糟的是**审计会留下"看过 3 个文件"的记录，出事后无法说明审核是否尽责** | 三条缓解，都不依赖"审核人自觉"：① **把必看项前置**——`PluginReviewFields` 在树的上方固定展示 `package.json` 的 `scripts`（安装脚本红线相关）、`dsh.bundle` 声明、以及**扫描报告的证据文件:行号清单**，审核人不必靠"翻树"才发现线索（§4.6 字段表 + §10.2）；② **敏感文件默认折叠但计数可见**——树上显示「可能含凭据（N 个）」，N>0 时审核页给一条显式提示（"该包内含 N 个可能含凭据的文件"），让"没看"变成一个有意识的决定；③ **可追溯**——`PLUGIN_SUBMISSION_FILE_VIEWED` 审计记录看过哪些路径（§7.6.5），出问题时可回看"当时看了什么"，必要时作为审核质量复盘依据。**不做**的：不强制"必须打开 N 个文件才能通过"（会诱导点开即算，把形式主义写进产品），也不做"未读清单拦截"——用流程卡人不如把线索送到眼前 |

> 其他已裁决、不再询问的：`name` 全站唯一 + 提交时 409 三分支（§1.3 D6、§4.1）、图标只取包内声明且按实际字节类型（§4.2、§8.1）、v1 不做分片索引（§8.3）、扫描披露不写进索引（§8.1）、撤掉最后一个可上架版本 → 插件自动转未上架（§5.2）、审核不因报告时效重扫（§14.1 A12）。

**可见范围变更的分期**：缩窄（`PATCH /api/v1/plugins/{ns}/{slug}/visibility` + 审计 + `markDirty`）随 **P1 治理**与「我的插件」完整态同批交付（个人空间 P0 只做"提交时选定"，不提供变更入口）；**放宽方向 v1 不交付**（§13 #22；§14.2 Q11 已于 2026-11-26 裁为不做），若后续版本要放开，需新增插件级审核主题并单独立批。"提交时选定三档 + 索引只收 `PUBLIC`"属 P0 范围——`PRD §8.2` 是索引契约的一部分，晚于此会让 P0 的索引口径与产品不一致（§16 S23）。

**规模红线**：不允许存在"能代发但没有扫描闸门"的版本——扫描闸门必须在代发之前（闸门顺序：扫描 → 审核 → 代发），且扫描闸门与代发必须在同一个 P0 交付单元内完成，P0 出口条件已包含真机验证（D7）与四裁决分支。本项目不设灰度放量，P0 即全量可用；开关只用于故障止血，不用于分阶段放出功能。**唯一例外是团队空间提交能力**（`SKILLHUB_PLUGIN_TEAM_SPACE_SUBMIT_ENABLED`）：它按 `PRD §6.1` 通用规则做成能力开关，P0 置灰、P1 翻开关，不是灰度，也不改前端代码。
