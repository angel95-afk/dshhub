### 7.6 暂存包文件浏览的安全约束（逐条写死，实现不得"灵活处理"）

这一节是 §7.2 三个端点的**规范正文**：每条都对应 §16 的一条回归断言。任何一条被"为了能看全"而放松，都必须显式改本节并留评审记录。

#### 7.6.1 路径穿越防护（三层，缺一层都不算实现）

| 层 | 时机 | 规则 |
|---|---|---|
| ① 物化阶段（已有，本次追加口径） | `PluginPackageMaterializer` 解包时 | 条目名规范化（POSIX 分隔符、折叠多余 `/`）后必须仍在包根内；**拒绝** `..` 段、以 `/` 开头、含盘符（`^[A-Za-z]:`）、含 NUL 字节、含反斜杠 `\` 变体；**符号链接/硬链接条目一律拒绝整包**（`plugin.error.archiveUnsafe`，同步 422），不接受"跳过链接继续"。理由：链接是唯一能让"包根内路径"指向包外的机制，放过它等于把前两层白做 |
| ② 请求白名单（本次新增） | `PluginStagedFileService.readText/openDownload` | 请求的 `path` 必须与清单中某一项**逐字节相等**（`String.equals`，大小写敏感）。实现上拿不到"目录 + 文件名拼接后 open"的路径——`PluginArchiveReaderPort` 只接受 `StagedFileEntry`，不接受任意字符串，从类型上消灭拼接 |
| ③ 读取时复核 | `PluginArchiveReaderPort.readEntry` | 命中的条目在 tar 里的名字与请求的 `path` 再比一次；不一致即 400。这一层防的是"清单缓存被脏数据污染" |

绕过口径（三个具体变体，必须都有测试）：

| 变体 | 处理 |
|---|---|
| URL 编码绕过（`path=%2e%2e%2fetc%2fpasswd`、双重编码 `%252e%252e%252f`） | 容器只做**一次** URL 解码；解码后的值进入第 ② 层白名单比对。因为白名单是"等于某个已有条目名"，`../x` 与 `%252e%252e%252fx` 都不可能等于包内条目名，**天然不命中**；同时对解码后仍含 `%` 的值直接 400（不做二次解码——"再解一次看看"是绕过者的入口） |
| 大小写绕过（`Package.json` vs `package.json`） | 白名单大小写敏感，**不**做 case-folding。不能在大小写不敏感的文件系统（macOS/Windows 开发机）上"看起来一样就放行"，否则线上（Linux）与开发机行为分叉，测试永远测不出线上问题 |
| 并发 / 竞争（同一提交被两个审核人同时浏览，期间暂存包被清理） | 读取是纯只读，无写放大；清单缓存用 single-flight 合并并发未命中（同一 key 只解一次，其余等结果）。对象在读取中途消失 → `410 stagedPackagePurged`（不是 500），且不清空已返回的清单缓存（清单本身仍可用于展示"曾有哪些文件"） |

#### 7.6.2 解压炸弹与资源上限（具体数值 + 推导）

| 限制 | 默认值 | 配置项 | 推导 / 理由 |
|---|---|---|---|
| 文件数上限 | `2000` | `SKILLHUB_PLUGIN_FILE_MAX_ENTRIES` | 上传 zip ≤ 50 MiB（既有口径）。前端类插件包典型 200–800 个文件（含 `dist/`），2000 留一倍余量；超过 2000 的多为误打包了 `node_modules` |
| 整包解压总量上限 | `200 MiB`（`209715200`） | `SKILLHUB_PLUGIN_FILE_MAX_UNCOMPRESSED_BYTES` | npm tarball 典型压缩比 3–4×，`50 MiB × 4 = 200 MiB` 作为绝对上限。超过它，单次遍历的 CPU/内存就不是"读一个请求"的量级 |
| 压缩比阈值 | 整包 `≤ 10:1`；单条目 `> 100:1` 且解压后 `> 4 MiB` 即判炸弹 | `SKILLHUB_PLUGIN_FILE_MAX_RATIO` | 正常代码/文本压缩比 3–5×，10× 已属"大量重复内容"；单条目 100:1 只可能是构造出来的（全零、单字符重复） |
| 单文件上限（可下载） | `8 MiB`（`8388608`） | `SKILLHUB_PLUGIN_FILE_MAX_ENTRY_BYTES` | 覆盖 `wasm`、字体、未压缩 `bundle.js`；再大就不是"审核看一眼"能解决的 |
| 文本内联预览上限 | `512 KiB`（`524288`） | `SKILLHUB_PLUGIN_FILE_MAX_TEXT_BYTES` | ≈ 8000 行源码，超过它审核人也不会在页面里滚；超限 413 引导下载，**不截断** |
| 清单请求预算 | `5s`（缓存命中 < 100ms） | `SKILLHUB_PLUGIN_FILE_INDEX_TIMEOUT` | 50 MiB gzip 完整遍历约 200–400ms，5s 是"机器慢/对象存储抖动"的容错，不是常态预算 |
| 单文件请求预算 | `10s` | `SKILLHUB_PLUGIN_FILE_READ_TIMEOUT` | 顺序解压到目标条目，最坏要走过整条流；含对象存储读 |
| 索引缓存 | TTL `10min`，最多 `200` 个提交 | `SKILLHUB_PLUGIN_FILE_INDEX_CACHE_TTL` / `..._INDEX_CACHE_MAX` | 键 = `(submissionId, sha512)`。审核窗口通常几十分钟到几小时，10 分钟 TTL 意味着一个审核人翻包只解压一次；200 个提交 ≈ 内存里几 MB 的清单条目，与 `PluginIndexReadCache` 同量级 |

**超限的语义是"拒绝这一次浏览"，不是"给你看一部分"**：返回 `422 stagedArchiveLimitExceeded`，页面明确写「该包超出可浏览上限（{limit}），请联系作者重新打包」——截断+静默会让审核人以为"看完了"，那比不给看更危险。同理，单文件超预览上限返回 413 而不是返回前 512 KiB。

#### 7.6.3 二进制判定（三条规则，任一命中即二进制）

1. **扩展名 / MIME 表**：`.png .jpg .jpeg .gif .webp .ico .woff .woff2 .ttf .otf .eot .wasm .node .so .dll .dylib .zip .tgz .gz .7z .pdf .mp4 .mp3` → 二进制（判 `detectedType`）。
2. **前 8 KiB 采样含 NUL 字节**（`0x00`）→ 二进制。文本文件（UTF-8/UTF-16 文本）正常不含 NUL；含 NUL 的"文本"几乎必然是编码错误的二进制。
3. **UTF-8 解码失败率**：按 UTF-8 严格解码前 8 KiB，替换字符占比 `> 5%` → 二进制。

三条都未命中才按文本返回。**不做"尽力解码"**：把二进制当文本返回只会产出乱码，让审核人以为包里有乱码内容（虚假信号比没有信号更糟）。

敏感文件标记（只标记、不隐藏、不阻塞）：`.env*`、`.npmrc`、`.yarnrc*`、`*.pem`、`*.key`、`*.p12`、`*.pfx`、`*.keystore`、`id_rsa*`/`id_ed25519*`、`credentials*`、`secrets*`、`.git/**`。理由：这类文件**恰恰是审核人最该看的**（"你有没有把凭据打进包里"），所以绝不隐藏；但要在树上打一个「可能含凭据」的徽标，避免审核人在投屏评审时无意展示。

#### 7.6.4 一致性（必须与 `sha512` 同一份字节）

| 场景 | 处理 |
|---|---|
| 正常 | 读到的 tarball 整包 sha512 与 `plugin_submission.tarball_sha512` 比对；`LISTED` 后回落比对 `plugin_version.sha512`。两者相等才返回内容 |
| 不一致 | `409 stagedPackageMismatch` + **不返回任何字节** + P1 告警（附 submissionId / 期望与实际的 sha512 前 16 位）。语义等同 §14.1 A13 的"代发前重算"——预览面先发现，代发面就少一次事故 |
| 暂存包已被清理 | `410 stagedPackagePurged`，页面显示「包内容已按保留策略清理」。**绝不**回退到私服、上游 npm、或"上一次同名的包" |
| 提交已被作者撤回 / `CANCELED` | 同 410（包可能已被清理）；报告与 sha512 仍在，页面照常展示元信息 |

#### 7.6.5 审计事件与字段（不记录内容）

| 事件 | 触发 | 记录字段 | 结果值 |
|---|---|---|---|
| `PLUGIN_SUBMISSION_FILES_VIEWED` | 清单读取成功/失败 | `submissionId`、`entryCount`、`sha512`（前 16 位）、`result`、`durationMs` | `ok` / `denied` / `purged` / `limit` |
| `PLUGIN_SUBMISSION_FILE_VIEWED` | 单文件读取 | `submissionId`、`path`、`size`、`binary`、`result`、`durationMs` | `text` / `binary` / `denied` / `notfound` / `mismatch` |
| `PLUGIN_SUBMISSION_FILE_DOWNLOADED` | 下载成功 | `submissionId`、`path`、`size`、`result` | `ok` / `denied` / `notfound` |

三条硬规则：

1. **不记录文件内容本身**。审计里只出现路径、大小、类型、结果——把内容抄进审计等于把"可能含凭据的文件"复制到第二处，还绕过了本节的访问控制。
2. **`path` 只在单文件/下载事件里记**（清单事件记条目数即可）；路径本身可能含内网信息（如 `config/prod-internal.yaml`），审计的读者是平台管理员，这一层可接受，但不再往上扩散（不进日志、不进埋点）。
3. **审计写失败即不返回内容**（`503 fileBrowseDisabled`）。预览是"管理员级能力"，**没有留痕就不该发生**；这与"埋点失败不影响功能"（§10.6）是两套口径，不要混。

#### 7.6.6 可见范围（与既有 403/404 口径一致）

**唯一判定依据是 `PRD §9` 矩阵，不是"看起来像管理员"**。「审核插件版本（团队空间）」一行：访客 —／空间成员 —／**空间管理员 ✓**／**平台管理员 —**。所以包内文件浏览 = 空间管理员 + 提交者本人；平台管理员**没有**这条权限，他们要看证据走矩阵「查看完整扫描报告与证据」那一行（`GET /api/v1/plugins/scan-reports/{id}`，本设计未改动）。v2.14 的 `PRD §6.5` 第 6 条已按矩阵收紧成同一句话。

| 访问者 | 结果 | 一致性说明 |
|---|---|---|
| 该空间空间管理员（`ADMIN`） | 可浏览 | 与 `PRD §9` 矩阵「审核插件版本（团队空间）」的 ✓ 同一行，不另立角色 |
| **平台管理员（`SKILL_ADMIN` / `SUPER_ADMIN`）** | **403** `noPermission` | 矩阵该行对平台管理员是 `—`。他们另有红线放行 / 黑名单 / 释放包名 / 软删，以及 `GET /scan-reports/{id}` 的完整报告与证据——**那些都不包含"读包内文件"**。给平台管理员开口子 = 实现了一个矩阵里没有的权限 |
| **平台管理员对 `PLUGIN_VERSION` 的 approve / reject** | **403** `noPermission` | 与上一行**同一个矩阵行、同一个理由**：没有包内文件读取权的人不该有审批权，否则审批就是盲签（§4.6 硬规则 3）。`subjectType=SKILL_METADATA` **不受此约束**——既有技能审核允许平台管理员，行为不变（§16 S16） |
| 提交者本人（`submitted_by == actor`） | 可浏览**自己的**提交；`canReview` 正常（自审允许），裁决按钮旁显示中性提示「你是本次提交的作者」 | 作者本来就知道包里有什么；允许他自查"审核人看到的是什么"，减少"我明明改了"的争议。能看也能批（用户裁决），但审计记 `selfReview: true`（§4.6 硬规则 4） |
| 其他空间成员（非 ADMIN） | **403** `noPermission` | 空间成员能看到"这个空间有插件"，但包内容是审核材料，不是空间公共资产 |
| 他空间成员 / 非成员 | **403** `noPermission` | 与"私有空间非成员 403、不泄漏存在性"同一口径（§13 #18） |
| 未登录 | **401** | 先认证再判权 |
| 提交不存在 | **404** | 与 `GET /submissions/{id}` 一致 |
| 已 `LISTED` 的提交 | 同一套规则（不扩大到匿名、不扩大到平台管理员） | 见 §6.4 第 3 条 |
